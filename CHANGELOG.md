# Changelog

All notable changes to **StackVend** will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Release entry convention

Releases are numbered steps `X.Y.Z-preview.K` (tag `vX.Y.Z-preview.K`) and roll-ups `X.Y.Z` (tag `vX.Y.Z`); a roll-up carries the same code as its last step and summarizes the steps since the previous roll-up. Every tagged release, step versions included, must include a section in this file with:

1. **Version heading**: `## [<version>] - YYYY-MM-DD` matching the Git tag `v<version>` (for example `## [0.9.1-preview.1] - YYYY-MM-DD` for the tag `v0.9.1-preview.1`).
2. **Host Terraform indicator**: an explicit `requires apply.sh: yes` or `requires apply.sh: no` line stating whether the release modifies host-platform infrastructure (`infra/platform/**`, `infra/modules/workflows/**`, or `workflows/**`).
3. **Upgrade run order**: the exact commands and order an operator must run after merging the release (for example, `bash scripts/apply.sh apply` first when `requires apply.sh: yes`, followed by `bash scripts/deploy-services.sh --all-jobs`). `PROJECT_ID=<id> bash scripts/upgrade.sh v<version>` runs this order for a release tag (read-only plan, confirm, apply, deploy, smoke check); the entry still lists the commands for operators who run them by hand.

Changes that are not released yet are listed under `## [Unreleased]`, directly above the newest release heading. A release renames that heading to its own `## [<version>] - YYYY-MM-DD` and starts a new, empty `## [Unreleased]` above it. There is no rule line (`---`) between release sections: a release's notes are its section, from its heading up to the next `## ` heading.

## [0.9.1-preview.2] - 2026-11-21

A security update, and the fix for **Update StackVend**. Every install and every fork should take it.

**requires apply.sh: yes**

**Upgrading:** on `0.9.0-preview` and `0.9.1-preview.1` the **Update StackVend** button cannot install this release: on those versions every press stops with `TAG_UNRESOLVED` (fixed below), and this release changes the platform Terraform, which the button never applies. Start no workload during the upgrade and let running ones finish. From a clean checkout of the repository you installed from:

1. Check the tag before anything of it runs (a fork names the official repository as `<remote>`, added with `git remote add stackvend https://github.com/asaslaw/stackvend.git`; otherwise use `origin`):
   - `git fetch --no-tags <remote> refs/tags/v0.9.1-preview.2:refs/tags/v0.9.1-preview.2`
   - `git cat-file -t refs/tags/v0.9.1-preview.2` must print `tag`, and `git for-each-ref --format='%(tag)' refs/tags/v0.9.1-preview.2` must print exactly `v0.9.1-preview.2`.
   - At the top of the checkout: `git -c gpg.format=ssh -c gpg.ssh.program=ssh-keygen -c gpg.program=false -c gpg.openpgp.program=false -c gpg.x509.program=false -c gpg.ssh.allowedSignersFile=scripts/release/allowed_signers verify-tag refs/tags/v0.9.1-preview.2` must pass (it prints `Good "git" signature for stackvend-release`), with the `allowed_signers` of the checkout you installed from (never the release's own list).
2. `PROJECT_ID=<id> bash scripts/upgrade.sh v0.9.1-preview.2` (a fork adds `--remote=<remote>`). It verifies the signature again, shows the read-only plan, asks you to confirm, runs `apply.sh apply` and then `deploy-services.sh --all-jobs`, and ends with a smoke check. Never pass `--trust-unsigned` for an official release.

By hand, after the same checks: `git checkout --detach 'refs/tags/v0.9.1-preview.2^{commit}'`, then `PROJECT_ID=<id> bash scripts/apply.sh apply`, then `PROJECT_ID=<id> bash scripts/deploy-services.sh --all-jobs`.

### Security
- **Control Center first-run sign-in.** On an install whose Control Center sign-in client is not pinned by Terraform, `POST /auth/config-client-id` took the first client from the request and could sign the caller in as an administrator. It no longer sets the first client or signs anyone in: it answers 401 or 403 to anyone not signed in as an administrator and `409 FIRST_RUN_CLIENT_OUT_OF_BAND` otherwise, and writes nothing. A first client now comes only from `cc_google_oauth_client_id` in the install's tfvars (or, for local development, the `GOOGLE_OAUTH_CLIENT_ID` environment variable); the sign-in page's first-run panel now shows those steps instead of a form. Administrator rotation of an existing client is unchanged. A Secret Manager error other than "not found" now counts as no client (sign-in is refused) instead of falling back to the Firestore value, and `/health` no longer reports whether a client is set. **Action:** a Control Center without IAP whose tfvars do not set `cc_google_oauth_client_id`: set it to the client you use and run `PROJECT_ID=<id> bash scripts/apply.sh apply`. A client saved earlier through the old form keeps working, but it cannot be told apart from one saved by someone else.
- **Live canary and recorded service URLs.** The terraform server now records a workload's service URL only when the Cloud Run API confirms that service; otherwise the URL is recorded as unknown with a typed reason and a `SERVICE_URL_UNKNOWN` warning (this includes GKE, load-balancer and custom-domain outputs, and services in another region). `scripts/live_canary.sh` probes only a confirmed URL, runs `curl` without your curl configuration and without following redirects, never sends your default `gcloud` identity token (a token goes only to a service that requires one, bound to that service's own URL), reports private workloads it cannot probe as not probed, and cleans workload text before printing it. It now needs read access to the child project and to the host's vending service; with a `gcloud` user login it sends no token at all, so private (IAM) workloads are reported as not probed. See [`documentation/live-canary.md`](documentation/live-canary.md) for what it sends and to whom. Run it only on workloads whose code and Terraform you trust.
- **Upstream sync workflow (forks and install repositories).** `.github/workflows/sync-upstream.yml` merged the newest upstream tag without verifying it. It now merges only an annotated tag whose own name is that tag, SSH-signed by a key in `scripts/release/allowed_signers` of your repository's default branch; anything else stops the run and pushes nothing. Its pull request lists every changed trust-anchor path (scripts, workflows, release keys, the upgrader and similar) and the tag's signer, and the optional `STACKVEND_SYNC_TOKEN` is used only by the push and pull-request step. **Action, for forks and install repositories with the sync on (Settings ▸ Upgrades):** scheduled runs use the workflow on your default branch, and the sync ignores pre-release tags, so no repository receives this workflow through the sync. Until you have merged it by hand after the checks in the README's "Opt-in upstream sync", keep `STACKVEND_UPSTREAM_SYNC` set to `false`, delete the token (`gh secret delete STACKVEND_SYNC_TOKEN`), and do not merge a sync pull request opened by the old workflow without the same checks.
- **`scripts/upgrade.sh` checks the tag's own name.** It refuses an annotated tag whose inner name is not the tag you asked for (`UPGRADE_TAG_NAME_MISMATCH`), also with `--trust-unsigned`, so an older signed release cannot be installed under a newer name. The `upgrade.sh` of `0.9.0-preview` and `0.9.1-preview.1`, which runs when you upgrade to this release, has no such check: that is why step 1 above checks the name by hand.
- **Assistant skills and code owners.** The repository's assistant skills (`.agents/skills/`) no longer tell an assistant to switch its sandbox off or to send your identity token to a workload; they probe only a confirmed URL without credentials, treat logs and records as data, and print commands only with values that pass fixed patterns. `.github/CODEOWNERS` now covers the agent instruction files and the trust anchors (it requests the maintainer's review; it enforces nothing).
- **Documentation.** The canary, sync and manual-upgrade sections now say what each tool sends and to whom, and every manual upgrade path verifies the tag first.

### Fixed
- **Update StackVend.** The button resolves the release tag correctly (it asked GitHub in a form GitHub does not answer), its first build step now fits Cloud Build's size limit (platform Terraform change), it builds with the same builder and run image as `scripts/deploy-services.sh` deploys, with the lifecycle version that builder names (all pinned by digest), and the Upgrades card links the build once it starts, after approval. After a button update, the Upgrades card no longer shows "Platform update pending" when the release needed no platform Terraform. The whole path (press, console approval, verified tag, build, deploy, health check) was run end to end on a test install against a test repository and a test key before this release. From this release on, the button can install later releases that change no platform Terraform (the next such release is its first official use).

### Known limitations
- After the **first** button update, do not use **Roll back services**: jobs cannot be rolled back yet (`ROLLBACK_UNAVAILABLE`, the result is partial). Go back with `scripts/upgrade.sh <previous tag>` instead.
- Approve in the Google Cloud console only a build whose `_REQUEST_ID` substitution matches a request you just made.

## [0.9.1-preview.1] - 2026-11-20

The first release step after the 0.9.0 preview. It changes how releases are numbered and published, not what StackVend does.

**requires apply.sh: no**

**Upgrading:** no platform Terraform change and no functional change to the running code. **Update StackVend** (Settings ▸ Upgrades) rebuilds every service and job from the signed release tag and moves them to the new version. By default an administrator then approves the build in the Google Cloud console (Cloud Build ▸ History) within 60 minutes; new workload runs are refused until the update ends (runs already started continue). Without the upgrader, run `PROJECT_ID=<id> bash scripts/upgrade.sh v0.9.1-preview.1` from the checkout you installed from: it verifies the tag's signature first, then shows the read-only plan and runs `apply.sh` (this release changes no platform Terraform) and `deploy-services.sh --all-jobs`.

### Changed
- **Release numbering.** Releases are now numbered steps such as `0.9.1-preview.1`, each with its own signed tag and its own section in this file, and roll-ups such as `0.9.1` that carry the same code as their last step and summarize the steps. Changes not released yet are listed under `## [Unreleased]`, directly above the newest release; `CONTRIBUTING.md` and the pull request template say so.
- **How releases reach this repository.** Each release now arrives as one pull request, merged by rebase onto `main`, followed by a signed tag on the merged commit. From now on each release adds to the history of `main` instead of replacing it.

## [0.9.0-preview] - 2026-11-18

First public preview. Read [`documentation/known-limitations.md`](documentation/known-limitations.md) before installing: it lists what does not work yet (regulated compliance profiles, workloads spread across several regions, Helm charts, per-workload billing budgets, automatic repair of running workloads, and more).

**requires apply.sh: yes**

**Upgrading:** this release changes the platform Terraform. Start no workload during the upgrade and let running ones finish (a run that starts a stage while the platform Terraform is applied can fail). Then run `PROJECT_ID=<id> bash scripts/upgrade.sh v0.9.0-preview`, which shows the read-only plan, asks you to confirm, runs `bash scripts/apply.sh apply` and then `bash scripts/deploy-services.sh --all-jobs`, and ends with a smoke check; or run those two commands yourself in that order. A new install behind Direct IAP (the installer's default) needs no Google OAuth client; a Control Center without IAP needs its own Web OAuth client (see Install requirements).

### Removed
- **Developer install mode and the Cloud Build push-deploy triggers.** Every install now works the way the default (Consumer) mode did: StackVend never modifies its own code or auto-heals its own services, and the installer no longer asks for a deployment mode. The release source follows signed release tags only (a stored branch or unsigned source reads as invalid, as it always did on a default install). A fork publishes signed release tags and points the release source at its repository, or deploys with `scripts/deploy-services.sh`. The Terraform variables `castor_deployment_mode`, `github_repo`, `cloudbuild_2nd_gen_repo_id` and `enable_cloud_build_triggers` are gone; an existing vars file that still sets them keeps working (OpenTofu warns about the undeclared values and ignores them; delete the lines to silence it). **Update StackVend** and its Cloud Build trigger are unchanged. requires apply.sh: yes (it removes the `CASTOR_DEPLOYMENT_MODE` environment variable from the platform services and jobs).
- **The unused `castor-webhook-signing-secret`.** The platform Terraform no longer declares this empty placeholder secret, which no service read. A new install does not create it; an existing install stops managing it on its next `scripts/apply.sh apply` (nothing is deleted: the empty secret stays in the project, unmanaged and free).

### Install requirements
- **OpenTofu 1.10 or later** to install or update the platform. `scripts/bootstrap.sh` and `scripts/apply.sh` check the version first and stop with a clear message on an older engine. The `gcloud beta` component is no longer needed.
- **Tag Administrator on the organization** for the person who runs the installer: it creates StackVend's deletion-safety tag, and StackVend only ever deletes projects that carry it. Without it (or without an organization and managed-workloads folder) the installer shows a prominent **NO DELETION SAFETY** warning with the grant command and asks `Continue without deletion safety? [y/N]` right after the folder question: **N**, Enter or no terminal stops before anything is changed (only when the platform state cannot be read does it ask later, before the plan); **y** completes the install, every delete is refused and Settings shows a warning. `scripts/apply.sh` prints the same warning (it never asks).
- **Folder IAM Admin** on the managed-workloads folder. Billing-account grants are optional at install time: when the installer cannot grant them, it prints the commands for a Billing Account Administrator to run afterwards.
- The installer's default ingress is **Direct IAP** (Google sign-in in front of the Control Center). Nothing but people calls the Control Center: its scheduled work runs as Cloud Run jobs.
- **Google OAuth clients.** Behind Direct IAP no OAuth consent screen or OAuth client is needed (press Enter at both client prompts). A Control Center without IAP needs its own Web OAuth client. The second prompt, for a tenant app sign-in client, is optional and not used in this preview; when you give both, they must be two different clients (the installer refuses identical client IDs).
- **`scripts/pre-bootstrap.sh` can grant the two organization roles.** When Tag Administrator or Organization Policy Administrator is missing for the person who will run the installer, and your account can read and set IAM on the organization, it offers each grant (both are organization-wide; only the full word `yes` grants it), then runs the read-only check again for up to 2 minutes and reports the grant done only when it passes (otherwise it warns and the installer checks again). It never grants without that answer, and with `--yes`, `--check-only` or no terminal it only prints the grant command, as before.

### Added
- **Build queue (Max Concurrent Builds).** Settings **Max Concurrent Builds** (default 1) limits how many builds that use the AI models run at once, so simultaneous submissions no longer compete for the install's model quota. A build over the limit is recorded as queued (the API answers 202 with its place in line), shows as *Queued (#n in line)* in the Flight Deck, can be cancelled there, and starts by itself when a running build ends. Fast-Path Deploy, Express, redeploy and IaC upgrades never wait. A build waiting for an approval gives its slot to the next build and takes one again (ahead of new builds) once approved. Service deploys only (orchestrator gateway and Control Center).
- **Control Center Guide tab.** A new **Guide** tab (before Settings, for every signed-in role) is a self-contained quick reference for everyday tasks (what to click, who can do it, what happens, the gotcha), with an in-page table of contents; it never sends you out of the Control Center. Its text is [`documentation/quick-guide.md`](documentation/quick-guide.md), whose per-section links to the full documentation are kept for repository readers and left out of the tab; sections only administrators can use are shown to administrators only (display only: every action keeps its own permission check).
- **Guide: Understanding Settings (administrators).** A new admin-only Guide section maps every Settings tab, lists the settings that change what StackVend does (with their defaults and when to change them), the ones safe to leave alone, and what the status and warning cards on the Parameters tab mean.
- **Test a spec locally (dry run).** Run a specification through the real generation pipeline on your machine and get a verdict (`WOULD_SUCCEED`, `WOULD_FAIL_AT:<stage>` or `INCONCLUSIVE`) and an HTML report, without creating anything in Google Cloud. See [`documentation/test-a-spec-locally.md`](documentation/test-a-spec-locally.md).
- **Typed per-service topology.** The architect's plan now states each service's compute type, which services it calls and what it reads, so hybrid workloads (for example GKE plus a Cloud Run edge service) are planned per service. The compute type comes from the plan, not from words in the specification.
- **VM worker compute type** (`compute-gce-worker` golden module) for background workers that need a virtual machine.
- **Agent Builder.** The agent-builder tool server scaffolds a real Agent Development Kit agent and can deploy it, with operator approval, to Vertex AI Agent Engine in the workload's own child project.
- **Workload code scanning.** The refactor scanner scans each workload's repository (Bandit) and raises at most one request per workload; scanner failures are reported instead of passing silently.
- **Billing grants in the platform Terraform.** When the person running `scripts/apply.sh apply` is a Billing Account Administrator, the install grants *Billing Account User* to the service accounts that vend child projects. Otherwise the install still succeeds and the Control Center Settings page shows the missing grant and the exact fix.
- **Gemini model support** for the Argon model family (per-family thinking settings and output limits), alongside the Flash models.
- **Gemini 4 Carbon** (`gemini-4-carbon`) can be selected for any model role in Settings. It gets the same request rules as Gemini 4 Argon (a fixed thinking level, no thinking budget) and its list price ($4 input / $20 output per million tokens) in the token cost figures. It is the default model of new installs (see Changed).
- **Any Gemini model in Settings.** An administrator may enter any Gemini model id. When the settings are saved, each changed model gets one small live call with its role's request settings; a model the API refuses, or that does not answer within 20 s, is not saved and the error names Google's reason. A model without built-in rules is tried with the Gemini 3.x request style, then the Gemini 4 style, and the style that works is stored and used by every agent. Its cost is shown as unknown until it has a price.
- **Thinking levels per role.** Settings has a thinking level (LOW, MEDIUM or HIGH) for the architect, developer, repair and other calls of Gemini 4-style models. The defaults are the levels used before (LOW, MEDIUM, LOW, LOW).
- **Typed infrastructure (generate mode), on by default.** New workloads declare their infrastructure as a typed intent that the platform checks and renders to Terraform (Control Center Settings, `governance.iac_intent_generate`). An administrator can turn it off per install; a value already saved in the settings is kept. Existing workloads keep their path; Cloud SQL, Redis, AlloyDB, Vertex AI endpoints and Bigtable are built on the typed path (the platform supplies the private network and the Cloud Run connector where needed); turning it off affects new workloads only. See [the user guide](documentation/user-guide.md#typed-infrastructure-generate-mode).
- **Known limitations** page: [`documentation/known-limitations.md`](documentation/known-limitations.md).
- **Specification size guidance.** The New Workload form says that results are best with specifications up to about 25,000 characters (longer ones are split and the lead developer reads the first 40,000) and that very large ones (over about 100,000) may fail to process, and shows a live character count under the specification (amber above 25,000, red above 100,000). It warns only; a long specification is still submitted.
- Comprehensive public **User & Operator Guide** at `documentation/user-guide.md` detailing the Control Center UI, Express vs. Document Spec Intake (uploads up to 25 MB), Flight Deck telemetry, sandbox lifecycles, and day-2 operations.

- **Update StackVend from the Control Center.** Settings ▸ Upgrades checks the release repository for a newer signed release and, when the release needs no `apply.sh`, offers **Update StackVend**: a Cloud Build run under a build-and-deploy-only identity that verifies the signed tag and redeploys the services and jobs, after an administrator approves it in the Google Cloud console. A new install has it from its first apply; **Disable update check** turns off every GitHub call for forks or network-isolated installs, which update with `scripts/upgrade.sh`.
- **`scripts/pre-bootstrap.sh`.** Optional first step: checks, read-only, every right the installer needs (blocking, degraded or optional, and what happens without it, with the exact grant commands), then creates or reuses the host project, links it to billing and creates or reuses the managed-workloads folder. Safe to re-run; it never deletes or changes an existing billing link. Its last step can start `scripts/bootstrap.sh` with the values filled in.
- **OpenTofu install offer.** When OpenTofu is missing or older than 1.10 (for example on Google Cloud Shell, which does not ship it), `scripts/pre-bootstrap.sh`, `scripts/bootstrap.sh` and `scripts/apply.sh` ask `Install OpenTofu 1.13.1 into ~/bin now? [y/N]`. Yes downloads the official release zip, checks its SHA-256 against the value pinned in the repository, and installs only the `tofu` binary into `~/bin` (no sudo, no package manager). No, or a run without a terminal, stops and prints the manual commands.
- **Approved deployable regions.** Settings **Approved Deployable Regions** lists the regions a new workload may use; the New Workload form asks for one (the default region, `us-central1`, first) and the workload builds and deploys there for its whole life, Express workloads too. The catalog card and the workload's page show its region. A workload whose region is no longer approved stops for an operator (`REGION_NOT_APPROVED`), and Settings refuses to remove a region a workload still uses (`REGION_IN_USE`). See "One region per workload" in [`documentation/known-limitations.md`](documentation/known-limitations.md).
- **Who may use this app, after creation.** Administrators see a **Who may use this app** card on a workload's page (or use `PATCH /api/workloads/<id>/access`) to change who may use a private app; the card warns that Private (Google sign-in) refuses personal Gmail accounts.
- **GitHub Actions deploy switch.** GitHub workloads get a per-workload **GitHub Actions Deploy** switch (on by default, on the create form and the workload's page). Off: no deploy workflow and no deploy identity, so every deploy goes through StackVend's pipeline.
- **Version record.** Every `scripts/deploy-services.sh` run records the release and commit of each service and job; Settings ▸ Upgrades shows them, marks anything not from a recorded deploy as unknown, and says in one line why there is no record yet.
- **`scripts/check-install-iam.sh`**, a read-only check of the rights an install needs, and **`scripts/live_canary.sh`**, which sends one example workload through a running install and follows it, read-only, to a deployed service and a `/health` probe ([`documentation/live-canary.md`](documentation/live-canary.md)).
- **Platform network card.** Settings shows, read-only, each platform component's ingress, network and egress mode from Cloud Run, and flags a service other than the Control Center that still accepts internet traffic (information until the install has the platform network, a warning after), a component off the platform network while a service is internal-only, or the QA sandbox job on the platform network.
- **App administrators for Private (Google sign-in) apps.** When a **Private: Google sign-in (IAP)** app with a Cloud Run service has an application-wide administrative role (for example SuperAdmin), StackVend sets the app's administrators on its Cloud Run services as `STACKVEND_APP_ADMIN_EMAILS`, and the generated app gives every listed address that role; other users get roles only from an administrator inside the app, and the app never makes its first visitor an administrator. The list is the signed-in Control Center account that created the workload (or the verified submitter of a platform-default workload) when that exact account is also a `user:` member of the app; otherwise it is empty, the build still succeeds and the workload shows the warning `APP_ADMIN.NONE_CONFIGURED`. There is no field to change the list yet: see [App administrators of a Private (IAP) app cannot be changed yet](documentation/known-limitations.md#app-administrators-of-a-private-iap-app-cannot-be-changed-yet). Existing Private (IAP) workloads get it on their next full build.
- **Environment variables the platform does not set.** Before commit, each Cloud Run service's code is read for environment variables with a fixed name that the platform never sets on that service; the workload page lists them (file, line and the fallback the code uses). A warning only: the build is not stopped. The golden Cloud Run modules now also set `GOOGLE_CLOUD_PROJECT` next to `PROJECT_ID` (a value the workload sets itself wins).
- **`scripts/upgrade.sh <tag>`** upgrades an install from the checkout you installed from: it verifies the release tag's signature, shows the read-only plan, asks you to confirm, applies the platform Terraform, deploys the services and jobs and runs a read-only smoke check. See "In-product upgrade" in [`documentation/known-limitations.md`](documentation/known-limitations.md).
- **Security and support documents.** [`documentation/threat-model.md`](documentation/threat-model.md) (trust boundaries, guards, residual risks), [`documentation/audit-and-roles.md`](documentation/audit-and-roles.md) (what is recorded where and what each role can do), `SECURITY.md` (report vulnerabilities through GitHub private vulnerability reporting) and `SUPPORT.md` (preview support: best effort, latest preview only).
- **Optional Data Access audit logs for the platform.** The platform Terraform setting `host_data_access_audit_logs` (off by default, no cost) can turn on Firestore write and Secret Manager read audit logs in the platform project; Cloud Logging volume is billed while it is on.
- **Replays of real failed runs guard every change.** The test suite replays recorded runs (a relaunch over an earlier build, a two-service public app, a reviewer outage, a deploy error inside a platform module, an inconsistent reviewer score, and clean runs) through the real developer and QA code, offline, and checks the outcome each run must reach, so a fix for one case cannot quietly break another.

### Changed
- **The installer and `scripts/apply.sh` back up the install's variables file for you.** `infra/platform/<project_id>.tfvars` is not committed, so the installer used to end by asking you to copy it to the state bucket by hand. It now copies it to `gs://castor-tfstate-<project_id>/platform/<project_id>.tfvars` itself at the end of the install, and `scripts/apply.sh apply` refreshes that copy after every successful apply (an earlier copy that differs is kept as `<project_id>.tfvars.prev-<UTC time>`). When the copy cannot be written, the install or apply still succeeds and prints `BOOTSTRAP_TFVARS_BACKUP_NOT_WRITTEN` or `APPLY_TFVARS_BACKUP_NOT_WRITTEN` with the retry. On a new machine or a fresh clone, `scripts/apply.sh` offers to restore the missing file from that copy (`Restore ...? [y/N]`), then stops so you can review it; without a copy it stops with `APPLY_TFVARS_MISSING_NO_BACKUP` and tells you to run the installer again. See [Configuration](documentation/configuration.md#backup-and-restore-of-the-vars-file).
- **The installer no longer asks for a Gemini API key.** `scripts/bootstrap.sh` no longer asks for an optional Google AI Studio Gemini API key: the Control Center assistant uses Vertex AI through the install's own identity, which is what pressing Enter at the old prompt gave. An install that already stores such a key in Secret Manager keeps using it when the installer runs again.
- **Long agent stages no longer hit the 30-minute workflow call limit.** The architect, developer and QA stages run as gateway jobs that report back to the workflow by callback, so a slow model (Gemini 4 Carbon developer runs take 10-20 minutes and sometimes over 30) no longer fails the run. Budgets: architect 30 minutes, developer 60, QA 45. Each stage runs as one execution of a new platform Cloud Run Job, `stage-runner` (the gateway's own image and identity), so it is not stopped when the gateway is idle or redeployed. A stage that does not report back in time ends the run as `STAGE_TIMEOUT`; a stage job that is stopped or crashes reports `STAGE_INTERRUPTED` (within about five minutes at most). A stage job runs only on the image the gateway runs: `scripts/deploy-services.sh` and **Update StackVend** copy the gateway's image to the job, and a mismatch stops the stage with `STAGE_RUNNER_IMAGE_SKEW` before any work. Cost: one job execution per stage (billed while it runs; a cold start of up to about a minute). If needed, `PROJECT_ID=<id> bash scripts/stage-jobs-switch.sh off` returns the stages to the previous synchronous calls at once (no deploy, no apply); after a gateway traffic rollback, `bash scripts/deploy-services.sh stage-runner` points the job at the image the gateway serves. requires apply.sh: yes (workflow, the `stage-runner` job and its run permission for the gateway); upgrade in the order of the Upgrading note above (`scripts/apply.sh apply`, then `scripts/deploy-services.sh --all-jobs`, or `scripts/upgrade.sh`), with no workload run in progress.
- **Every agent stage has a deadline.** Each gateway stage stops starting new model calls when its budget runs out, answers `STAGE_DEADLINE_EXCEEDED` with the stage and how far it got, and never commits, opens a pull request or merges after it has answered, or after its run ended, was replaced by a newer run, or the emergency stop was switched on. A stage that finishes in time behaves as before.
- **A failed deployment goes back to the AI only when the AI's own code failed.** When OpenTofu rejects a workload's configuration, StackVend now checks which file the error is in. An error in the AI's code is repaired as before; an error in a platform module or file stops the run as `PLATFORM_DEFECT`, one in a file you wrote stops it as `OPERATOR_REQUIRED`, a plan error that does not happen again stops it as `PROVIDER_TRANSIENT` (run Fast-Path Deploy), and a failure nothing can attribute (including every failure during the apply itself, a failed `init` and a failed container build) stops it as `DEPLOY_FAILURE_UNATTRIBUTED`. Each stop names the failing file and resource, and the run's debrief shows the class. Before, every such failure was sent to the AI for up to two rewrites, which could not fix a platform file and could break working code.
- **A too-slow AI call now moves to the next model of the fallback list.** Every developer-stage model call (work breakdown, each code task, the infrastructure task, repairs, single-call generation) has a time limit (4 to 15 minutes by kind of call, never more than the stage has left). A call that takes longer, or that fails with a temporary Google error (429, 500, 503, 504; a 429 or 503 is first retried once after 4 seconds), is abandoned and the next model of the fallback list is asked, with that model's own request settings; a late answer is never used, and its billed tokens still count in the run's token use. A run can therefore mix models: the Flight Deck shows which model wrote the developer's output, for example "written by gemini-4-carbon; task-db by gemini-4-argon (fallback: timeout)". When no model answers in time the developer stage stops with a typed error that lists every model tried, instead of running until the 30-minute step limit.
- **A new workload's GitHub repository is named after the workload, without a prefix.** Repositories of a GitHub organization are visible to its staff, so the internal `castor-` prefix is gone from them: a workload `payment-service` gets `<organization>/payment-service` (the workload id, lower case, `_` becomes `-`) when **Target GitHub Repository** is left empty. Existing workloads keep the repository they have recorded (a `castor-<id>` repository keeps working: pull requests, merges, deploys, decommission). Because the bare id can already be taken by another repository of the organization, vending never uses an existing repository that it did not record for that workload: the vend stops with `GITHUB_REPOSITORY_NAME_TAKEN` (stage `vcs_repository_vending`), nothing is pushed or changed, the workload no longer names that repository, and the message says to rename or remove that repository, create the workload with another id, or enter another existing repository in **Target GitHub Repository**. Vending records the name for the workload before it creates the repository, so a re-run of the same workload (also after a GitHub error during the create) reuses its own repository; when GitHub cannot be read the vend stops with `GITHUB_REPOSITORY_UNREADABLE` (run it again). If a workload's repository was deleted and a repository of the same name created since, the vend stops with `GITHUB_REPOSITORY_ID_CHANGED` and the workload keeps its record: remove or rename the new repository, then restore the original from the organization's Deleted repositories and run again (on a Shared runner install, renaming the new one and re-submitting the workload with that name in **Target GitHub Repository** also works; a Per-workload install's runner pin refuses another repository). Re-submitting an existing workload on the New Workload form with an empty **Target GitHub Repository** keeps the repository it has.

So personal GitHub accounts are no longer supported for repository vending: the installer asks for the GitHub organization, repository creation no longer falls back to the signed-in user's account (an owner that is not an organization stops with `GITHUB_OWNER_NOT_ORGANIZATION`, nothing created), the Settings VCS card shows **Owner Not an Organization** for a personal-account owner, and the documentation and Control Center no longer offer a personal access token. A `pat` key already in the secret (or `GITHUB_PAT` / `GITHUB_TOKEN`) is still read as a fallback token for organization repositories; it does not enable personal accounts and will be removed in the next release. Serverless Git is unchanged.
- **Gemini 4 Carbon is the default model.** New installs use `gemini-4-carbon` for every model role (architect, developer, FinOps advisor, Control Center assistant; repair follows the developer) with `gemini-4-argon`, then `gemini-3.8-flash`, then `gemini-3.7-flash` as the fallback models, so a busy Gemini 4 model falls back to a Flash model with its own capacity. Existing installs keep the models their saved settings name, fallback list included. Carbon costs several times more per run than `gemini-3.8-flash` (about 4.5 times on simpler examples, 6 to 9 times on harder ones in offline evaluations); an administrator can pick any Gemini model id per role in **Settings** (checked with one live call on save). The architect, developer and compliance agents now always lead with their Settings model (compliance uses the architect's): the `GEMINI_MODEL` environment variable no longer goes ahead of it. On an existing install this changes the model of the architect, developer, lead, swarm juniors, critic, spec decomposer and single-call path to the one Settings names (before: the `GEMINI_MODEL` environment variable, `gemini-3.7-flash` by default, wherever it was not already in the Settings cascade); an install with no saved Settings gets Carbon. When the settings cannot be read, or a saved model id has no request rules, the services keep leading with `GEMINI_MODEL` and log a warning instead of switching to Carbon. The After-Action Report is written by the Control Center Assistant Model and its fallbacks instead of retired Gemini 2.x ids; when no model answers, the deterministic report records why (`AAR_MODEL_UNAVAILABLE` / `AAR_MODEL_CALL_FAILED`).
- **New workloads start with Code Freeze on.** A new Control Center setting, *Freeze new workloads by default* (`governance.freeze_new_workloads`, on by default), makes every new workload (created, promoted, or submitted as a Google Doc spec) start frozen: its first build and deploy run, and so do builds an operator starts, but SRE auto-healing, the code scanner's pull requests and Upgrade IaC wait until an operator clicks **Unfreeze** on the workload's page. Turn the setting off to have new workloads start unfrozen. Existing workloads are not changed, and a re-create, re-vend or redeploy now keeps a workload's current freeze, SRE auto-healing and code scanner switches instead of resetting them (new workloads still start with both switches on).

It now honours the setting; if the settings cannot be read, human code review stays on.

With no verified submitter, nobody is listed and the build stops with `ACCESS_POLICY_INCOMPLETE` until an administrator lists who may use it. Nothing from the specification text is ever listed. Public stays an explicit choice. Existing workloads keep their current access. Express workloads get the same default and the same **Who may use this app** choice, applied to every Cloud Run service they deploy.
- **Drive folder auto-discovery is off by default.** Docs intake polls only the configured inbox folders (`INBOX_FOLDER_ID` / `IN_PROGRESS_FOLDER_ID`) until authorized submitters are supported; an administrator can turn discovery on in Settings (`governance.drive_folder_auto_discovery`).

In the reference test set (nine example specifications, three builds each) all 27 builds produced code and infrastructure that passed `tofu validate`, the Python checks and the QA gate.

You can still turn it off explicitly. The Cloud SQL, AlloyDB and Spanner modules now validate with the pinned Google provider (6.35.0).

A new account that has not accepted the Google Cloud Terms of Service, or any failed API enable, now stops the installer with a typed error instead of continuing.

It now shows a prominent **NO DELETION SAFETY** block with the grant command and asks `Continue without deletion safety? [y/N]`: **y** continues as before; **N**, Enter, or a run without a terminal stops (`BOOTSTRAP_TAG_ADMIN_DECLINED` / `BOOTSTRAP_TAG_ADMIN_UNCONFIRMED`). The question comes right after the folder question, before the installer enables an API or writes anything; an install whose tag already exists is not asked. `scripts/apply.sh` prints the same block and never asks.
- **Settings says where to run `apply.sh`:** every fix that needs it names the folder you installed from (it holds `infra/platform/<project_id>.tfvars`).
- **Empty Workloads Catalog** points to **New Workload**; it no longer offers to register StackVend itself as a workload.

- **QA repairs what QA found.** When QA's tests fail, the AI reviewer also reviews that build and one repair round gets both results; a QA retry repairs the files QA named, starting from the tested build's own files. In the QA sandbox only, the toolchain's pinned `pytest` / `pytest-timeout` win over a workload's own pins (the deployed app is unchanged).

Registered modules may not grant public access by themselves.

- **Security controls baseline.** The create form's compliance field is now **Security controls baseline**, with a warning that FedRAMP, HIPAA and CJIS compliance need an Assured Workloads folder of that regime; workload records show *Compliance* only for a matching Assured Workloads folder.
- **Refused destructive actions** in the Control Center show their code, detail and guidance (the message was hidden under the confirmation dialog), and the release stage shows the real approval outcome.
- **Update StackVend and internal-only services.** When the terraform server accepts only internal traffic, the upgrade's `/validate/ready` check reports `NOT_CHECKED` (`INGRESS_INTERNAL`) without calling it, instead of failing the upgrade. Whenever a finished upgrade's check says `NOT_CHECKED`, Settings ▸ Upgrades now asks `/validate/ready` itself with the Control Center's identity and shows `READY`, `NOT_READY` (with the reason) or `NOT_CHECKED`.
- **Serverless Git 404s are typed.** The git server marks every answer with `X-StackVend-Git-Server: 1`; a 404 without it (for example Cloud Run refusing a caller) now fails with `GitServerUnreachable` instead of being read as "repository not found". `scripts/deploy-services.sh` and Update StackVend deploy the git server first, alone, and stop before its clients if it fails.

- **Scheduled spend sync, sandbox sweep and billing alerts run as Cloud Run jobs, not as calls to the Control Center.** With Direct IAP on, IAP refused the service account the two schedulers and the billing-alert push used, so the nightly spend sync and sandbox sweep failed every night and billing alerts never arrived. Now `castor-finops-nightly-spend-sync` runs `finops-spend-sync-job`, `castor-sandbox-workload-sweeper` runs `sandbox-workload-sweeper-job`, and a new scheduler `stackvend-billing-alert-drain` runs `billing-alert-drain-job` every 30 minutes, which reads the billing-alerts subscription (now a pull subscription). Each job runs the same code as the Control Center did, as its own least-privilege service account, writes Firestore, and reports a run record and an exit code. The Control Center accepts no service-account callers any more; the spend sync and sandbox sweep stay available to administrators as manual triggers.

Before, a breach was never enforced. Turn it off with `billing_breach_enforcement_enabled = false`. StackVend still creates no budgets: see [`documentation/known-limitations.md`](documentation/known-limitations.md).
- **A missing deletion safety tag is shown on every page.** While the deletion safety tag is not set up (the installer was not an organization Tag Administrator), a banner at the top of every Control Center page, for every signed-in user, says StackVend can't delete or decommission the projects it creates until a Tag Administrator re-runs `apply.sh apply`; administrators get a button to the Settings card. The new-workload and Deploy to Folder forms say the same above the submit button (submitting still works). A lighter banner points to the one-click tag backfill while older projects are untagged, and a status that cannot be read shows *Couldn't check deletion safety status*, never an all-clear. Before, only a card on Settings, **Parameters** said so.
- **QA checks the app's own authentication code.** The QA security reviewer reports as blocking an identity taken from an unverified header or token, a check that passes when verification could not run, a placeholder credential in non-test code and a bypass switch that is on by default. QA's static phase also refuses three such shapes outright, read from the parsed code: a token decoded without its signature check (`SEC.UNVERIFIED_TOKEN_DECODE`), refusals that are unreachable while an on-by-default switch is on (`SEC.AUTH_OFF_BY_DEFAULT`) and a literal bearer token (`SEC.LITERAL_BEARER_TOKEN`). A build with one of these now fails QA and goes to the repair, where it used to pass.
- **Plans that need internal-only Cloud Run stop early.** When a workload's compliance decision requires internal-only ingress and the plan has a Cloud Run service (which cannot be internal-only yet), the run stops at the compliance stage with `COMPLIANCE.PRIVATE_INGRESS_UNSUPPORTED`, before the plan approval, the child project and any code, instead of failing at the apply every time.
- **A Public app's push-only worker is flagged.** In a Public workload every Cloud Run service is public, including a worker that only a Pub/Sub push subscription calls. The compliance stage now warns (`ACCESS.INTERNAL_SERVICE_PUBLIC`) for each such service and the run pauses for plan approval, with the warning on the approval card; choose Private to make every service private. Access itself does not change.
- **Spot batch workers stop after 24 hours.** A Spot VM from the `compute-gce-worker` module gets a maximum run time (`max_run_duration_seconds`, default 24 hours), after which Compute Engine deletes it, so a runaway worker no longer bills forever. Standard workers are unchanged.
- **Variables the platform sets cannot be overridden.** Before every apply, the deploy checks that each variable the platform sets for the workload (project, region, image, access settings and so on) has exactly the platform's value in the plan; a variables file or another value that changes one stops the deploy for an operator with `APPLY.ROOT_VARIABLE_OVERRIDDEN` (naming the variable, never its value), and nothing is applied.
- **QA stops on platform-rendered files say what the file comes from.** When QA fails on a file the platform renders (for example `infra/workload/topology.json` or `main.tf`), the `PLATFORM_DEFECT` stop now lists what that file is rendered from and says whether it is a platform capability gap or an architect/topology issue. A QA failure on `infra/workload/custom.tf.json`, which the platform renders from the AI's `iac_intent.json` plus platform tables (fact expressions, required arguments, generated secret versions), is now repaired through the intent instead of regenerating the whole build; the repair is told the file comes from the intent and platform tables. The QA record's `hcl_syntax_passed` is empty (not checked) instead of `false`, because QA does not check HCL, and the release certificate says "HCL syntax not checked by QA".

### Fixed
- **The architect's plan no longer asks for files StackVend deletes.** StackVend builds every container image itself with Buildpacks and writes the workload's CI itself, so the developer stage removes any Dockerfile or `.dockerignore`, every `.github/workflows/` file except the platform's `deploy-<service>.yml`, and, on a GitHub workload, the root `cloudbuild.yaml`. A plan task that named one of these could never be met: the QA reviewer then failed a clean build for the "missing" file (example 01), or the file was dropped without a word (about a third of recorded example 04 plans). The architect stage now checks the final plan's typed target files against these exact rules, after the plan review and before anything is vended. A plan with no such file is unchanged and costs no extra model call. Otherwise the architect is asked, at most twice, to re-plan without the listed files and without the instructions that ask for them; a re-plan that changes the reviewed compute decision (archetype, services) is not used. When no re-plan is usable, StackVend removes the listed files from the reviewed plan and says so in the plan document under "Platform plan contract"; a CI file that is a plan task's only sign for the QA reviewer that the platform's CI facts apply stays listed (StackVend still deletes it), so the reviewer is told what it was before. A model outage during the re-plan (rate limit, no answer) no longer fails a run that would have passed: that re-plan turn counts as failed and StackVend removes the listed files from the reviewed plan, as above. An outage of the architect's first answer still fails the stage as before. The outcome is recorded in the architect stage trace (`plan_contract`). The plan StackVend writes itself when the model gives no build plan (about one run in three) no longer has a CI step asking for `cloudbuild.yaml` and docker build. IAM roles named in a task's text are not checked by this; the existing architect and QA rules for refused roles still apply. Service deploys only (orchestrator gateway with the stage-runner image).
- **QA no longer fails a build for an image build file the platform provides.** StackVend builds every container image itself with Buildpacks and removes AI-written build and CI files, but the QA reviewer was not told so and could fail a clean build because a build file a plan task asked for (for example a `cloudbuild.yaml` that runs Buildpacks) was "missing" (example 01). The reviewer is now told how images are built, and such a finding counts as met by the platform only when it points at platform build files or at a CI or infrastructure task whose files are all platform build files; a finding about the app's own files (for example its `Procfile` or `requirements.txt`) still fails the build. Workloads on a virtual machine are unchanged. Service deploys only (orchestrator gateway).
- **A Cloud SQL instance that Google finishes creating no longer fails the deploy.** The Google provider stops waiting for a Cloud SQL instance create as soon as Google reports a passing internal error on the still-running operation, and forgets the instance, although Google then finishes creating it. After such a failed apply the deploy now reads its own create operation from the Cloud SQL Admin API, waits for it (up to 25 minutes), imports the finished instance and applies once more. A create that Google really fails, that is still running after the wait, or whose instance is not running stops with `CLOUDSQL_CREATE_UNRESOLVED` for an operator (nothing is deleted). When a workload creates several instances, the ones this deploy created are all imported or none. A relaunch that meets an existing running instance of the workload's own name now imports it instead of stopping with `APPLY_ADOPTION_UNRESOLVED`. An instance that is not running, has a `root` user open to any host, or whose planned create restores a backup is never imported. For MySQL this means such a create always stops for an operator: the provider removes the default `root` user open to any host only after a create it waited for, so an operator removes that user (or the instance); a PostgreSQL instance is imported.
- **A workload over Google's project quota fails with its own error class.** When Google refuses to create a workload's project because the project quota is exhausted, vending now stops with `VENDING.PROJECT_QUOTA_EXCEEDED` (recognized from the create operation's status code and `QuotaFailure` detail, never its text) instead of `DEPENDENCY_FAILED`. The message names the project, says the quota belongs to the creating account and the organization, that projects pending deletion count toward it for about 30 days, and where to raise it (Known limitations). The old message, which blamed the billing account and suggested a specification field that does not exist, is gone; any other refusal shows Google's own error. Service deploy only (project vending).
- **A new GitHub workload repository no longer shows a failed GitHub Actions run.** StackVend's merge of its pull request into the workload's branch started the repository's deploy workflow about 3 seconds later, before StackVend's first deploy had created the workload's identity federation pool, so every new repository's only run failed at Google sign-in (`invalid_target`), although the workload deployed and was healthy; on a re-run of an existing workload that run would have raced StackVend's own deploy. StackVend's merge commit (the automatic release merge and the merge after an approval in the Control Center) now ends with GitHub's `[skip actions]` directive, so GitHub starts no workflow for that one commit. This also skips the repository's own push workflows for that commit; later pushes run as usual. Serverless Git merges are unchanged. See [GitHub Actions deploy of a workload](documentation/known-limitations.md#github-actions-deploy-of-a-workload-preview). Service deploys only (orchestrator gateway with the stage-runner image, and the Control Center).
- **QA no longer fails a workload for a role StackVend refuses to grant.** When the architect's plan asked for a privileged IAM role (live: `roles/iam.serviceAccountTokenCreator` for Cloud Scheduler's OIDC token), the QA reviewer reported it missing, but StackVend's IAM policy refuses that role in every workload's infrastructure, so no repair could add it and the build stopped after its repair rounds (example 02). When the reviewer names one of the refused roles for an infrastructure task of the plan, the build is no longer failed and no repair is attempted: the QA summary lists the finding as a documented platform limitation (advisory), see [Workload infrastructure cannot grant privileged IAM roles](documentation/known-limitations.md#workload-infrastructure-cannot-grant-privileged-iam-roles). A finding about any other role, or any other missing grant of the same task, is judged and repaired as before. The QA summary and the release certificate name the refused role. The architect is now also told which roles StackVend refuses, so its plans stop asking for them; a plan that genuinely needs one says so in its risk assessment. Service deploys only (orchestrator gateway).
- **GKE pods can act as their Google service account.** A GKE workload's Kubernetes service account (in `k8s/*.yaml`, annotated with `iam.gke.io/gcp-service-account`) needs a Workload Identity grant (`roles/iam.workloadIdentityUser`) on that Google service account, or every Google API call of its pods fails. With the typed infrastructure file (`infra/workload/iac_intent.json`) the developer agent could not write that grant, and StackVend did not add it either, so the QA reviewer's finding could never be repaired (example 04 stopped after three repair rounds). For a workload with a GKE Autopilot service the typed infrastructure now has one exact entry for it: a `google_service_account_iam_member` with that role and a `gke_service_account` member (namespace and name). StackVend renders the member as `serviceAccount:<project>.svc.id.goog[<namespace>/<name>]` and applies the grant after the cluster exists. The role is refused with any other member and on any other resource type, and the member is refused for a workload without a GKE service. Service deploys only (orchestrator gateway and stage-runner image).
- **QA no longer fails a GKE workload for the cluster's network.** StackVend puts a GKE Autopilot cluster on the project's `default` network with private nodes; a workload cannot declare a dedicated subnet, secondary ranges or Cloud NAT. When the QA reviewer still reports one missing for a plan's infrastructure task, the build is not failed and no repair is attempted: the finding is listed as a documented platform limitation (advisory), see [GKE clusters use the project's default network](documentation/known-limitations.md#gke-clusters-use-the-projects-default-network). Service deploys only (orchestrator gateway).
- **GKE manifests in their own namespace now deploy.** A workload whose `k8s/*.yaml` put its objects in a namespace other than `default` (example 04: `stream-apps`, with a `Namespace` manifest) passed QA and then always stopped at the deploy with `K8S_MANIFEST_APPLY_FAILED` for an operator: the `Namespace` manifest was refused as a cluster-wide kind, and nothing created the namespace. The deploy now creates each namespace the manifests name, if it does not exist yet, before the dry run, and never changes an existing one. A `Namespace` manifest may hold only its name and the standard `app.kubernetes.io/` labels; anything else in it is refused and goes back to the developer agent for repair. A system namespace and every other cluster-wide kind are still refused for an operator, and StackVend never creates a namespace whose name starts with `kube-`, `gke-` or `gmp-`. Workloads that use only the `default` namespace are unchanged. See [GKE workloads: only five placeholders are filled in manifests](documentation/known-limitations.md#gke-workloads-only-five-placeholders-are-filled-in-manifests). Service deploys only (Terraform server and the `tf-applier` job image).
- **A file the architect's plan names is written before QA, not discovered missing by it.** When the plan's task list named a file (for example `apps/<service>/models.py`) and the developer agent put that code somewhere else, every check before QA passed and the QA reviewer's "missing file" finding sent the whole build back for a full regeneration, even when all its tests passed. The developer agent's pre-commit checks now report a plan file the build lacks (`PLAN.TARGET_FILE_MISSING`), and its own repair step writes it in the same round. Only files inside the platform's layout count: a service's own files, the root `tests/` of a single-service workload, the root `README.md` and the applied `k8s/` manifests.
- **GKE manifests use the file name the plan gives.** When the architect's plan names a manifest such as `k8s/deployment.yaml`, the developer agent is now asked for that file instead of `k8s/<service>.yaml`, so the build and the plan agree. Without such a name in the plan, nothing changes.
- **Tests that import from their own `conftest.py` are no longer broken by StackVend.** StackVend added a `tests/__init__.py` file to every test folder, which makes `from conftest import ...` in a test file fail with "No module named 'conftest'". The file is no longer added to a folder whose tests import their own `conftest.py` that way; every other folder still gets it.
- **Generated tests of GKE workloads see the manifests as they are committed.** StackVend fills the `${PROJECT_ID}`, `${PRODUCT_ID}`, `${REGION}`, `${SERVICE_NAME}` and `${ARTIFACT_REGISTRY}` placeholders in `k8s/*.yaml` before the commit. The developer agent's test writer used to read the manifests with the placeholders still in them, so its tests asserted the placeholder text and failed in QA against the real values. It now reads them with the values filled in, exactly as committed, and a QA repair of a test is shown the committed manifests too.
- **A QA reviewer finding that asks to delete an infrastructure entry can now be fixed.** When the QA reviewer found, for example, a duplicate Cloud Scheduler job in the workload's typed infrastructure file (`infra/workload/iac_intent.json`), the developer agent's repair that deleted the duplicate was always refused, because no finding was allowed to justify a deletion; the run then stopped after its repair attempts. The reviewer now also names the exact entries that must be deleted to meet a finding, and a repair may delete exactly those (entries of the reviewed file, checked exactly; nothing else may be deleted). The next QA round reviews the result again.
- **A repair round now has 15 minutes instead of 6.** One slow model call that times out and falls back to the next model could use up most of the old 6-minute round, leaving the repair no time to call a model again. The per-round repair time (`repair_wall_clock_s`) is now 900 seconds; the round's token budget and number of attempts are unchanged.

It now stops before such an attempt and reports the time limit (`WALL_CLOCK`), and attempts that asked no model are no longer counted.

Before, nothing passed the generated password to the app, so it could not sign in (AlloyDB already worked this way). An existing workload gets this at its next build; Upgrade IaC and a re-apply do not change it.

Before, the manifests were never applied and the deploy still reported success; now a manifest that cannot be applied fails the deploy with `K8S_MANIFEST_APPLY_FAILED`. Before, it was replaced by the stopped state and a restore said "restored" while VMs and Cloud SQL stayed stopped.

When an earlier quarantine was interrupted, a resource that has been started since is restarted by the restore too. Billing is detached only after the billing account has been recorded, or when it cannot be read, only if a restore still knows which account to re-link.

The reviewer now sees the REWORK request (following it is not a missing requirement), and the correction turn gets the request ahead of the review notes, the quota snapshot and the draft plan to patch. Service deploy only (orchestrator gateway).

A plan made section by section gets no automatic correction turn; if section-by-section planning fails and the spec is planned in one turn instead, that plan gets the correction turn as usual. Service deploy only (orchestrator gateway).

Service deploy only (orchestrator gateway).

- **Opening a workload from the catalog shows that workload.** The page's first load could replace the workload you opened with the first one in the list.
- **The installer no longer stops when the install's variables file already exists.** `scripts/bootstrap.sh` used to stop whenever `infra/platform/<project_id>.tfvars` existed. It now reads the platform state: for an install that was never applied it backs the file up and continues as a new install; for an applied install it asks `Re-run the installer for it?` (Yes keeps your values, with a backup). A `terraform.tfvars` (which OpenTofu would load by itself) is renamed to `<its project_id>.tfvars` or backed up instead of refused.
- **A run that stops after QA keeps the tested branch and pull request.** When a rebuild after a QA failure stopped (for example on a file the platform renders), StackVend had already closed the tested pull request and deleted its branch. Earlier pull requests are now closed only once a new build has committed its own files (a stop at commit time keeps them too, and a stage that already timed out or was stopped closes nothing), and the stop's message names the branch, commit and pull request it kept.

### Security
- **The GitHub credential is no longer on git command lines.** The platform's git commits passed the GitHub installation token in the command's arguments, where it was visible to the process table and was logged in full when a clone or push timed out. Git now receives it through its environment, only for commands that reach GitHub, and git errors name the command and the timeout only.
- **A Google Drive spec can no longer pick any workload by its title.** A Workload Manager can send Drive specs only to a new workload or one assigned to them (as in the Control Center), nobody can target the StackVend platform itself (the gateway and project vending refuse it too, so the host project is never used as a workload project), and a title that does not give a valid workload id stays in the inbox with a reason. Every build request now needs a valid workload id, and the Control Center create form and Deploy to Folder refuse ids it would not build. When two Drive documents in the same poll ask for the same workload, only the first is built; the other stays in the inbox (`SPEC_WORKLOAD_ALREADY_REQUESTED`) and is checked again on the next poll. A retrigger or infrastructure re-apply of the StackVend platform record in the Control Center is refused up front (`PLATFORM_WORKLOAD_RUN_REFUSED`) instead of being answered as sent and failing later. A Workload Manager who starts a new workload from Drive is assigned to it as its Workload Manager (recorded in the Access Control audit as `USER_ACCESS_AUTO_ASSIGNED`), so their later Drive specs for it are built; existing workloads and their assignments are not changed.
- **Only the Control Center is public.** Every other platform service (gateway, vending, MCP tool servers, SRE sentinel, spec ingestion, Serverless Git server) accepts internal traffic only, on top of IAM: the platform's own services and jobs reach them through a new platform network `stackvend-host` (by default Direct VPC egress for `*.run.app` only, a private `run.app` DNS zone and a Private Service Connect endpoint for Google APIs; no NAT, other outbound traffic unchanged), and same-project Pub/Sub, Scheduler and Workflows count as internal. The QA sandbox job is never on that network. A new install is internal-only from the installer's first apply (`scripts/bootstrap.sh` writes `host_vpc_egress = true` and `host_internal_ingress = true`). An existing install turns it on in two applies: the first puts the services on the network with ingress unchanged; then set `host_internal_ingress = true` and run `scripts/apply.sh apply` again (refused with `APPLY_HOST_INGRESS_BEFORE_NETWORK` while the network is not applied). `host_egress_mode = "NAT_ALL_TRAFFIC"` switches to all-traffic egress through Cloud NAT; `host_network_deployer_grants` adds a subnet `roles/compute.networkUser` for the trigger and upgrader identities if deploys need it. `scripts/apply.sh` and `scripts/bootstrap.sh` read the host's effective `run.allowedVPCEgress` / `run.allowedIngress` organization policies before the plan and stop with `*_HOST_NETWORK_ORG_POLICY_REFUSED` when one refuses. Operators can no longer `curl` those services or use `gcloud run services proxy` (break-glass: `documentation/configuration.md`).
- **App code can no longer add Terraform to a workload's Firestore index file.** The composite indexes StackVend writes to `infra/workload/indexes.tf` came from collection and field names in the app's queries, written as they were; a name with a quote could add resources to that platform file. Names are now escaped, and a name Firestore would not accept (or one holding a control character) stops the build with `FIRESTORE_INDEX_ID_INVALID`.
- **Separate OAuth clients.** The Control Center and the (future) sign-in for generated workloads never share a Google OAuth client: `scripts/bootstrap.sh` refuses identical client IDs, so a tenant app cannot sign platform administrators into the Control Center.
- **Pinned engine checksums.** The validation service runs an OpenTofu binary only after its downloaded release archive matches a pinned checksum; an engine version without a pinned checksum is refused.
- **Deploys run only a verified engine.** Workload deploys and plans now use the same pinned checksums: the OpenTofu or Terraform release archive must match before it is unpacked, a binary already on the machine is never used, and pinned checksums cover the versions the Settings offer (OpenTofu 1.8.8, 1.9.0 and 1.10.0, Terraform 1.5.7, copied from the official release checksum files), and any other version fails with `ENGINE_UNVERIFIABLE`. The engine download now times out instead of hanging.
- **Sensitive outputs stay hidden.** An OpenTofu output marked `sensitive` is no longer stored, returned or shown in clear text: the deploy record, the deploy result and the Control Center's workload details show `(sensitive value)`, and resource attributes the engine marks sensitive are left out of the details view.
- **No deletes outside the plan.** A deploy no longer deletes child resources on its own: errored GKE clusters and VPC connectors are listed for an operator after a capacity failure (`errored_stubs`) instead of being deleted, and a subnet range conflict fails with `SUBNET_CIDR_CONFLICT` instead of deleting the other subnet.
- The gateway authenticates to the compliance server, and builds stop with `COMPLIANCE_UNAVAILABLE` when it cannot be reached.
- **Provider allow-list.** Workload OpenTofu runs install only the `google`, `google-beta`, `kubernetes` and `random` providers; any other provider in the configuration or state stops at init with `PROVIDER_NOT_ALLOWED` for an operator.
- **OpenTofu time limits.** A workload OpenTofu command that runs too long is stopped and the deploy fails with `TOFU_TIMEOUT` for an operator.
- **Documented trust model.** Only platform administrators should be able to push Terraform to workload repositories; see "Trust model" in [`documentation/known-limitations.md`](documentation/known-limitations.md).
- **New installs run workload Terraform per workload.** `scripts/bootstrap.sh` writes `tf_runner_identity = "PER_WORKLOAD"` and `tf_runner_dedicated_sa = true`, so a new install deploys each workload as its own deployer in its own project, with the Terraform runners on their own service accounts, from its first apply. An existing install stays Shared until an operator moves it (Settings switch, backfill, then step B); see "Terraform runner identity" in [`documentation/configuration.md`](documentation/configuration.md#terraform-runner-identity-shared-or-per-workload).
- **Verified provider downloads.** Provider archives that the platform mirrors from the OpenTofu registry are checked against a committed, signed SHA-256 table; a mismatching provider is left out of the mirror and OpenTofu downloads it itself, with its own signature check.
- **GitHub tokens only for known callers.** Project vending hands out a GitHub token only to an allow-listed caller identity, and a workload's GitHub Actions identity federation trusts only the workload's recorded branch.
- **A workload's page shows only its own Terraform state, without secrets.** The Control Center no longer reads another workload's state file whose name starts with the same letters (for example `app-billing` for `app`), masks outputs that OpenTofu marks sensitive, drops attributes it marks sensitive, shows only fixed non-secret attributes per resource, and shows state outputs to Workload Managers and administrators only (Viewers see a note instead).
- **Other websites cannot act in the Control Center for you.** A request that changes something is refused (`CSRF_CROSS_SITE_REFUSED`) when the browser says another site sent it, so a page you visit while signed in cannot start a build, a deploy or a sandbox sweep. The Control Center's own page and scripts are unaffected, including through the CLI proxy (`gcloud run services proxy`).
- **The Control Center can read each workload's own logs.** Project vending grants the Control Center's service account `roles/logging.viewer` on every child project it vends (a vend whose grant fails stops with `VENDING.CC_LOG_READER_GRANT_FAILED`); for workloads vended earlier an administrator runs `POST /api/settings/cc-log-reader/backfill` once (additive, idempotent, audited). No platform Terraform change.
- **Upgrade IaC records who really clicked it.** The audit record, the commit author name and the pull request now always name the signed-in caller; an `author` sent in the request body can no longer put someone else's name there.
- **A refused Express deploy cannot be applied through a relaunch.** When an Express deploy was refused because it would delete or replace existing resources, a Fast-Path relaunch (chosen by hand or by Auto) is now refused with `DESTROY_REQUIRES_APPROVAL` just like **Deploy Infrastructure**, and the gateway refuses any other Fast-Path run of that workload, until the workload is re-submitted in Express mode.
- **QA sandbox job kept off the platform network.** The gateway refuses (`QA_JOB_DRIFT`) a QA job attached to the platform network `stackvend-host`, where untrusted generated code could reach internal-only platform services.
- **Workload IaC can no longer grant secret access on the whole project.** A generated workload that grants a Secret Manager role (such as `roles/secretmanager.secretAccessor`) or an IAM-admin role at project level, written with a literal role, is now stopped before commit (`IAC.PROJECT_WIDE_GRANT` on the typed IaC intent, `POLICY.PROJECT_WIDE_GRANT` on hand-written-style Terraform) and sent back to the developer agent, which grants the role on the one secret it reads instead. Grants that StackVend's own modules make (for example a database module's access to its password secret) are unchanged.

See the [roadmap](documentation/README.md#roadmap) for ideas under consideration; nothing there is scheduled.
