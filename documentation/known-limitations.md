# Known Limitations (Public Preview)

StackVend is in **public preview**. This page lists what does not work yet, or works only in a narrow way, so you can decide what to try and what to avoid. It describes the code in this release. Where this page and the code disagree, the code wins: please open an issue.

> **Use a disposable environment.** Install StackVend in a dedicated Google Cloud project, under a test organization or folder, with a billing account you can afford to put at risk. Review every generated change before it is applied. See also [`SECURITY.md`](../SECURITY.md).

## What the preview has been tested on

* The nine [reference examples](examples/README.md), three builds each (27 builds), generated from scratch with live model calls. All 27 produced code and infrastructure that passed the offline checks: `tofu validate` on the generated infrastructure, Python checks on the generated services, and the QA gate.
* These checks run **offline**. They show that the generated project is well formed, not that it deploys and serves traffic. Live runs, from specification to a deployed workload, are measured separately: in the release checks on 29 and 30 October 2026, 4 of 6 runs (29 October) and 3 of 6 runs (30 October) were deployed and verified, across two development installs. The other runs did not reach a verified deployment. A page with the per-run live results will be linked here. <!-- live results page: add the link when it exists -->
* One build is a sample, not a guarantee: the models are not deterministic. To try your own specification without creating anything, see [Test a Spec Locally](test-a-spec-locally.md).

## Trust model: who may change a workload's Terraform

Read this before you give anyone access to a workload repository.

* **Only platform administrators may push Terraform to workload repositories.** StackVend applies the Terraform in a workload repository's `infra/workload/` folder, whoever wrote it. AI-written Terraform is checked before commit. Terraform that a person pushes is checked only at apply time: before every apply StackVend checks the plan and refuses provisioners, modules from outside the workspace, providers outside the platform's set and reading another workload's state. Those checks look at the finished plan, and Terraform data sources are read while the plan is made, with the runner's credentials (next point). Give write access to workload repositories (and to their `main` branch in particular) only to the people you trust as platform administrators.
* **Test-only imports add their packages to the service.** When a single-service workload's tests import a package (for example FastAPI's `TestClient`, which needs `httpx`), StackVend adds that package, with a minimum version, to the service's `requirements.txt` so QA can run the tests. The added minimum can conflict with an old exact pin elsewhere in the file (for example `fastapi<0.110` with an added `starlette>=0.36.0`); the build then stops with an unresolvable-requirements error that names both lines. A declared `httpx2` still gets `httpx` added as well.
* **On a Shared install, the Terraform runner can read platform secrets and read or change every workload's state.** On a Shared install the `tf-applier` job and the `mcp-terraform-server` service run as one platform service account (`sa-castor-developer`). That account can read platform secrets in Secret Manager (for example the GitHub App private key), read every object in the platform state bucket and write every workload's Terraform state in it (objects under `workloads/`). It cannot write the platform's own state (`platform/`). Terraform runs with that account's credentials, so anyone who can push Terraform to a workload repository can read those secrets and read or change other workloads' state with ordinary Google provider resources. The install setting **Terraform runner identity** (`tf_runner_identity`, see [Configuration](configuration.md#platform-variables-project_idtfvars)) chooses between **Shared** (this behaviour) and **Per workload** (each workload deploys as its own deployer in its own project). A new install made with `scripts/bootstrap.sh` is Per workload from its first apply, with its runners on their own service accounts, so this limitation does not apply to it. An existing install stays Shared until an operator moves it (Settings switch, backfill, then step B). On a Shared install, and on a Per-workload install until its runners run as their own service accounts (`tf_runner_dedicated_sa`, step B), this limitation applies. How to move an install: [Terraform runner identity](configuration.md#terraform-runner-identity-shared-or-per-workload).
* **The Terraform runner can also change platform settings and workload records.** The same account can read and write the platform's main Firestore database, which holds the platform settings and every workload's record (only the separate guard database that holds deletion records and approvals is protected). Terraform pushed to a workload repository could therefore change platform settings or another workload's record. This is the same trust boundary as above, and it applies where the point above applies: only platform administrators may push Terraform.
* **Budget notifications are trusted by content, and project Owners and Editors can send them.** The breach policy acts on messages on the `billing-budget-alerts` Pub/Sub topic. StackVend acts only on a message whose `billingAccountId` attribute is this install's billing account and whose budget maps exactly to a workload (the workload's recorded budget id, or a budget named `budget-<workload id>`), and it takes the spend threshold, the target project and the policy from the workload's own record, never from the message. But Pub/Sub does not prove who published a message, and anyone who may publish to the topic (by default every project Owner and Editor of the host project) can write a message that passes these checks and so trigger the workload's breach policy (for example scale to zero). Topic IAM cannot remove that: IAM grants are additive, and the Owner and Editor roles include publishing. Treat host-project Owner and Editor as platform administrators.
* **No shared Google sign-in in the preview.** Do not store anything in the Secret Manager secrets `castor-oauth-client-id` / `castor-oauth-client-secret`: a new install never writes them, and any value stored there may be passed to workload Terraform. Set the Control Center's own client with `cc_google_oauth_client_id` in the install's vars file and `scripts/apply.sh apply`. See the next section.

On a Shared install, and on a Per-workload install before step B, treat every workload repository as having the same trust level as the platform's own repository.

## Per-workload Terraform runner identity is new

The **Per workload** runner identity is new in this preview, and some operations do not work with it yet. New installs are Per workload, so these points apply to every new install. On a Per-workload install:

* **Plan, saved-plan apply and drift check are refused.** They stop with `RUNNER_MODE_UNSUPPORTED`, also when an agent asks for them through its plan or drift tool. No pipeline step uses them; normal deploys are not affected. They will run as `tf-applier` executions in a later release.
* **Between step A and step B, Express deploys, vending redeploys and force-unlock are refused.** Each stops at once with `RUNNER_PAYLOAD_STAGING_FAILED`, and nothing runs. Until step B the runners still run as the platform account, which cannot write the runner staging bucket. Step B ends this; switching the install back to Shared restores them too.
* **The result of an Express deploy, a redeploy or a force-unlock is not signed yet.** Each of these runs as one `tf-applier` execution, which writes its result to the platform database. The Terraform server uses that result only when vending's signed record shows that this exact execution picked up its credentials, but the result itself is not signed. A platform service that can write the platform database and knows the run's id could replace the result while the run is going, so the reply could report the wrong outcome. What was applied is not affected: it ran as the workload's own deployer. A later release has vending sign the result too. When a reply says the run may still be going, check the run and the workload's state before you retry.

The steps that move an existing install (step A, the mode switch, the backfill and step B) are described in [Configuration](configuration.md#terraform-runner-identity-shared-or-per-workload).

## Other security gaps in this preview

* **The GitHub Actions deploy path skips StackVend's checks.** While a GitHub workload's **GitHub Actions Deploy** switch is on (the default), anyone who can push to the workload's branch can change the running app: the generated `.github/workflows/deploy-<service>.yml` builds and deploys the pushed code with `sa-gh-deployer`, without StackVend's pre-commit checks, QA or plan approval (infrastructure is still applied only by StackVend). Turn the switch off on the workload's page to make every deploy go through StackVend's pipeline; the next pipeline run deletes the workflows and the next deploy removes the identity federation pool, provider and deployer account.
* **No prompt-injection screening.** Specifications, uploaded documents and **StackVend Assistant** questions are passed to the models without a prompt-injection screen (Google Cloud Model Armor is planned). Accept specifications only from people you trust; Drive intake already accepts only documents owned by verified administrators, workload managers and approvers. When QA fails with a code defect, each repair round sees QA's findings and a size-limited part of the test output, which the workload's own generated code produced. That text is marked as untrusted data in the prompt, which is prompt hygiene, not a screen.
* **Existing installs accept internet traffic until they turn internal-only ingress on.** A new install is internal-only from its first apply (see "Platform services other than the Control Center are internal-only" below). On an install with `host_internal_ingress = false`, every platform service, not only the Control Center, accepts requests from the internet; only callers with a valid Google identity token and the invoker right get through. The **Platform network** card in Settings lists those services as information while the install has no platform network (`stackvend-host`), and as a warning once it has one.
* **QA checks three authentication mistakes, and nothing more.** The QA job reads the generated Python, without running it, and fails the build, with the file and line, when it finds any of these in a non-test file:
  * a token library asked not to check the signature (`google.auth.jwt.decode` with `verify=False`, PyJWT or python-jose `decode` with `verify_signature` off, python-jose `get_unverified_claims`) (`SEC.UNVERIFIED_TOKEN_DECODE`);
  * a function that can only refuse a request (HTTP 401 or 403) when a module-level setting read from an environment variable is switched away from a literal default of on, so the check is off unless someone sets the variable (`SEC.AUTH_OFF_BY_DEFAULT`);
  * a function that returns a fixed string, in the same file, whose result is sent as `Authorization: Bearer ...` (`SEC.LITERAL_BEARER_TOKEN`).

  The finding goes to the normal QA repair. **Passing this check does not mean an app's sign-in or permissions are correct.** It recognizes these exact code shapes only: anything written differently, spread across files, or read from a value it cannot trace is not reported, and it says nothing about whether the right people are allowed in. There is no way to turn a finding off, so two valid uses are also refused and must be written another way: decoding a token without checking it, unless a later statement in the same block verifies that same token with a key (for example, to read `iss` first and then verify); and reading the expiry of a token the service fetched for itself. A default-on setting that restricts something other than sign-in, combined with a request check, is reported too. Files outside the build's own draft are scanned like any other: on an existing repository, a finding in a file this build did not write cannot be repaired and the run regenerates.
* **The QA sandbox has normal internet access.** The job that runs a workload's generated tests (`qa-sandbox-test-runner`) can reach the internet. Its service account has no roles, and it can only write its own two result files.
* **Automated QA is not a security review.** QA runs the workload's generated tests, static checks and an AI review of the changes. It does not attack the running app, and a generated login or permission check can pass every test and still be wrong, or lock out real users, because generated tests usually simulate sign-in. Have a person review generated authentication and authorization code, and try it with real accounts, before production use.
* **Registered modules cannot be public, and the check reads only literal settings.** Who may use a workload is set by its access record, through the golden compute modules. A module you register in **Settings > Modules & Bundles** may not grant public access by itself: registration (and a code or Git ref change) is refused with `REGISTERED_MODULE_PUBLIC_EXPOSURE` when the module's Terraform gives `allUsers` or `allAuthenticatedUsers` an IAM role or storage access, sets a public storage ACL (`publicRead`, `publicReadWrite`, `authenticatedRead`, or a public `role_entity`), turns off the Cloud Run invoker check (`invoker_iam_disabled = true`, or the `run.googleapis.com/invoker-iam-disabled` annotation on a first-generation Cloud Run service), or passes `allow_unauthenticated = true` to a module it calls, even behind a `count` switch. Every `.tf`, `.tf.json`, `.tofu` and `.tofu.json` file of the module is read, subdirectories included. A Private workload that uses such a module registered before this check stops with the same error before anything is committed (Express and Agent mode), and so does a Private Express workload whose module parameters name `allUsers` or `allAuthenticatedUsers`; **Sync** marks the module `ERROR` with the reason. In a Private Agent-mode workload, AI-written Terraform that passes `allUsers` or `allAuthenticatedUsers` to any module call (golden or registered) as a literal argument value, or as a value or key inside a literal list or object, is refused before commit and sent back to the developer for repair (`POLICY.PUBLIC_PRINCIPAL_IN_MODULE_CALL`, naming the module and the argument); if the repair does not remove it, the run stops before anything is committed. A variable used in the call is read the way OpenTofu reads it: from the variables files OpenTofu loads by itself in `infra/workload/` (`terraform.tfvars`, `terraform.tfvars.json`, `*.auto.tfvars`, `*.auto.tfvars.json`; this check reads that directory only, and the AI may not write any of them there or at the repository root, see the next item), else its default. Escape sequences inside a value (`\u0041`) are not decoded. Public workloads, and Express workloads created before private-by-default, are unchanged. Limits: "by itself" means the literal settings and variable defaults in the module's own files. Not checked: values computed by an expression (`each.value`, `local` values, `toset([...])`, `jsonencode(...)`, a JSON policy document written as a string), including a member passed to a module call through such an expression, escape sequences inside a value, other settings of a module called from inside the registered module, a sibling directory the module reads (`../x`), resources that are public by design without any IAM member (App Engine versions, API Gateway gateways), ingress or load balancer settings, and a Git module whose branch moves after registration. A Git module is read whole from its repository when it is registered: a repository with more than 2,500 files cannot be registered, and a failed read asks you to try again later.
* **Variables files and `.tofu` files: only the AI's are refused.** OpenTofu loads `terraform.tfvars.json`, `*.auto.tfvars` and `*.auto.tfvars.json` in a workload's root module by itself, and `.tofu` / `.tofu.json` files like `.tf` files (a `.tofu` file replaces the `.tf` file of the same name). The platform owns a workload's root variable values, so a variables file of that kind written by the AI (in `infra/workload/`, or at the repository root, where a deploy also reads `terraform.tfvars`) is refused before commit (`POLICY.TFVARS_NOT_ALLOWED`, naming the file) and sent back to the developer, who returns it empty and gives the variables defaults instead; a `.tofu` / `.tofu.json` file written by the AI, in any directory, is refused the same way (`POLICY.TOFU_FILE_NOT_ALLOWED`) and comes back as a `.tf` file in the same directory (with typed infrastructure the AI writes no Terraform: it comes back empty, and each declaration it held is named in the finding and not kept). If the repair does not remove it, the run stops before anything is committed. This applies to every workload, in both IaC modes. Such files that you commit to the workload repository yourself are not refused before commit. At deploy, every variables file of that kind that OpenTofu would load by itself (at the repository root or directly in `infra/workload/`) is checked before anything is built: a symbolic link (`APPLY.TFVARS_SYMLINK`) or a file that sets a variable the platform sets itself (the sign-in secret variables `oauth_client_secret` / `firebase_api_key`, and `project_id`, `region`, `product_id`, `github_repo_full_name`, `container_image`, `oauth_client_id`, `firebase_auth_domain`, `github_repository_id`, `github_default_branch`; `APPLY.TFVARS_OVERRIDES_PLATFORM`) stops the deploy for an operator, naming the file and the variable, and a file whose variables the platform cannot list stops it for an operator too (`APPLY.TFVARS_UNPARSEABLE`). That last stop includes a valid file the pinned python-hcl2 cannot read (for example a continuation line that starts with an operator inside parentheses): OpenTofu's own parser then says whether it is broken, and the message says when it is not. Before each apply, the plan itself is checked as well: a variable the platform sets (the ones above, the GitHub Actions deploy switch `enable_github_actions_deploy` when the platform sets it, and the access variables when the platform applies the workload's access record) that your code declares must have exactly the platform's value in the plan, whatever set it; otherwise the deploy stops for an operator with `APPLY.ROOT_VARIABLE_OVERRIDDEN`, naming the variable, and nothing is applied. Otherwise the file is applied as committed: a variables file of yours can still set the access variables (`allow_unauthenticated`, `enable_direct_iap`, `authorized_invoker_members`) of a workload without an access record (and of a Public or Express workload), and a `.tofu` file of yours is not read by the pre-commit checks. A file a person has not changed is never refused, even when the developer returns it unchanged during a repair. StackVend does not record these file kinds as the AI's, so such a file that an AI run committed before this check is treated as yours: it is left alone and applied as committed. Delete it from the repository.
* **Changes to or from Public need a full relaunch.** Administrators change who may use an app on the workload's page (**Who may use this app**) or with `PATCH /api/workloads/<id>/access`. Changes between private records (people added or removed, IAM callers only ↔ Google sign-in) apply with **Fast-Path Deploy**, which applies the current access record. A change to or from **Public**, or to a Public app, needs **Full Swarm Rebuild**, and a widening needs that full build's plan approval first (Fast-Path Deploy is refused until then). Express workloads apply an access change when the Express form is submitted again.

## Generated public apps have no shared Google sign-in yet

The installer asks for a tenant Google sign-in client, but no release uses it yet: generated apps get no shared "Sign in with Google", there is no switch to turn it on, no sign-in hub, and no app gets its own Google sign-in client. A **Public** app handles its own sign-in, if it needs one; for Google sign-in in front of an app today, choose **Private: Google sign-in (IAP)** when you create the workload. AI-written Terraform that sets up Google sign-in itself (Identity Platform configuration or identity providers), uses the sign-in module in a private workload, or grants a role that can read a shared sign-in secret is refused before commit and sent back to the AI for repair.

* **Authorization inside a Public app is not verified.** Any sign-in or permission checks inside a Public app are part of the AI-written application code, and StackVend does not check that they work (QA refuses only the three patterns listed under *QA checks three authentication mistakes, and nothing more*). Use **Private: Google sign-in (IAP)** for anything sensitive.
* **The access mode comes from the form, not from the specification.** A specification that says an endpoint is "public" (for example example 01's webhook) is still built with the access chosen in **Who may use this app** when you create the workload, and the default is **Private: Google sign-in (IAP)**, which refuses callers outside your organization. Choose **Public** for an app that anyone on the internet may call.
* **A Public app requires sign-in on its API routes.** In a Public app the generated code requires the app's own sign-in on every route under /api/ except GET /api/config, and there is no setting yet to make other API routes public. Anonymous callers such as third-party webhook senders, machine clients without a sign-in, or guest checkout are refused on those routes.

## Private (IAP) apps admit only organization accounts

**Private: Google sign-in (IAP)** apps, the default for new workloads, use Identity-Aware Proxy with a Google-managed OAuth client. Google documents that such a client admits only accounts of your Google Cloud organization (Google Workspace or Cloud Identity).

* A personal Gmail account, or any account outside your organization, is refused with "You don't have access", even when it is listed under who may use the app.
* List organization accounts as the app's members, for example `user:ana@your-company.com`, `group:team@your-company.com` or `domain:your-company.com`.
* The Control Center behind Direct IAP (the installer's default) works the same way: sign in to it with an organization account.
* **Private: IAM callers only** does not use IAP sign-in, so this limit does not apply to it.
* A custom OAuth client that would also admit personal accounts is a future feature; this release has no setting for it.
* **Pub/Sub push into a Private (IAP) app is not delivered.** StackVend gives the push identity the IAP accessor role, but Google-managed IAP accepts only tokens addressed to an allowlisted OAuth client, which this release does not have, so pushed messages are refused and retried until the subscription's retention ends. A **Private: IAM callers only** app receives pushed messages. For an event-driven app behind IAP, use a pull subscription or the **Private: IAM callers only** access mode. This lifts with the custom OAuth client feature.
* **Changing a workload's access mode does not rewrite its login code.** The access mode changes who can reach the app; the application code already generated stays as it was, including how it identifies the signed-in user, and a later build is told to keep existing code. An app written for one access mode and moved to another, for example from public sign-in to **Private: Google sign-in (IAP)**, can refuse every request or trust the wrong identity. After a change of access mode, have a person check the app's authentication code and correct it in a reviewed change.

## App administrators of a Private (IAP) app cannot be changed yet

When a **Private: Google sign-in (IAP)** app has a privileged role (for example SuperAdmin or Admin), StackVend sets the app's administrators on its Cloud Run services as the environment variable `STACKVEND_APP_ADMIN_EMAILS`, and the generated app gives every listed address its highest role. Other users get roles only from an administrator inside the app. The app never makes the first visitor an administrator.

* **Who is listed:** the person who created the workload in the Control Center (the signed-in account StackVend verified), but only when that exact account is also listed as a `user:` member of the app. A `group:` or `domain:` member is never made an administrator. For a workload created with the platform default, the verified submitter is used the same way.
* **Nobody is listed** when the creator is not a `user:` member of the app, or the workload was created before this release. The app then has no administrator: nobody holds its privileged role. The build still succeeds; the workload record shows the warning `APP_ADMIN.NONE_CONFIGURED` (`app_admin_contract`) and the QA judges report it as configuration, not as a code defect.
* **Changing the list is a future feature.** The create form, the API and the **Edit access** card have no field for app administrators yet. To get an administrator today, create the workload from the Control Center while signed in as that person and list the same account as a `user:` member.
* The list is applied by a full build (Agent mode). When an access change alters the list (for example the creator is removed from the members), an **Auto** relaunch runs a full build instead of a Fast-Path Deploy; a Fast-Path Deploy chosen explicitly does not change the list.
* Existing Private (IAP) Cloud Run workloads get the list, the rule and the QA checks on their next full build. An older app that makes its first user an administrator gets a critical security finding from QA on that build, and the developer replaces the bootstrap.

## Regulated compliance profiles are not available yet

You choose a workload's compliance profile (HIPAA, FedRAMP Moderate, FedRAMP High, CJIS, PCI DSS or EU regions) explicitly; StackVend never guesses it from the words in the specification (see [Choosing a compliance profile](user-guide.md#choosing-a-compliance-profile)). The regulated profiles are not ready yet:

* The compliance review during the build is **advisory**: it adds required tasks to the plan, but it does not check the generated infrastructure. It stops a run only for typed reasons: an invalid or conflicting compliance profile, or a decision that requires internal-only ingress on a plan with Cloud Run services (see [below](#cloud-run-services-cannot-be-made-internal-only-yet)).
* The check that blocks is at apply time. Before every apply, StackVend checks the plan against the workload's profile and **refuses the apply** when a data store has no customer-managed encryption key (CMEK), Data Access audit logging is missing, or a resource is in a region the profile does not allow. Data stores that the AI writes directly (for example Firestore databases, Pub/Sub topics, Cloud Storage buckets, Secret Manager secrets and Cloud SQL instances) often have no encryption key, so expect most regulated builds to be refused at apply.
* A profile is a **security controls baseline**, not a compliance status. FedRAMP, HIPAA and CJIS compliance require an Assured Workloads folder of that regime; a baseline chosen in an ordinary folder applies the baseline's technical controls (customer-managed encryption keys, audit logging, allowed regions) but does not make the workload compliant. StackVend shows "Compliance: <regime> (Assured Workloads)" only when the profile comes from the folder's Assured Workloads regime, and otherwise "Controls: <regime> baseline (not a compliance environment)".
* **Assured Workloads folders are not detected.** Reading a folder's Assured Workloads regime needs `assuredworkloads.workloads.list` at organization level for the compliance server's account, which the installer does not grant yet. Every folder is therefore read as an ordinary folder: the stricter-profile rule and the refusal of unmapped regimes (for example IL4 or ITAR) do not apply, and the profile you select is used. Each run's compliance answer records the reason (`assured_workloads_check`: `AW_CHECK_FAILED` with the HTTP status, or `AW_CHECK_ORG_UNKNOWN`). In an Assured Workloads folder, select the folder's regime yourself.
* Treat regulated profiles as **not supported** for now. Do not use StackVend for regulated data.

## Cloud Run services cannot be made internal-only yet

A generated Cloud Run service in a workload always accepts traffic from the internet at the network level; StackVend cannot yet set a per-service private (internal-only) ingress. Per-service private ingress is planned.

* If the specification wording asks for it, the folder's organization policy `constraints/run.allowedIngress` requires it, or the compliance profile requires it (today only `PCI_DSS`), and the plan has a Cloud Run service, the run **stops at the compliance stage**, before anything is built or changed, with `COMPLIANCE.PRIVATE_INGRESS_UNSUPPORTED`. The message names the input that asked for it. By then the architect has already run (its model calls are the only AI spend), because the plan has to exist to know whether it contains a Cloud Run service.
* To proceed, remove the requirement, or plan the workload without Cloud Run services (GKE or VMs only: those plans are not stopped, and the apply check applies to Cloud Run services only). With the requirement gone, you can protect the services with IAM only (authenticated callers with a verified identity token); that is not a way around a compliance profile or organization policy that requires internal ingress.
* The check reads the plan, not your files. A workload that sets internal ingress through its own override file (for example `infra/workload/human_override.tf`) also stops at this check, even though that override would satisfy the apply check.
* The apply-time compliance check is unchanged: it still refuses any Cloud Run service that lacks internal ingress under such a decision.
* The specification words that ask for it are `no public ip`, `internal only`, `private ingress` and `internal load balancer`.
* **In a Public app, every Cloud Run service is public.** Who may call a service is decided once for the whole workload. A service that only Pub/Sub push, Cloud Scheduler, Eventarc, Cloud Tasks or Workflows call, for example a worker the specification calls internal, still accepts requests from anyone on the internet. A push subscription sends an identity token, but neither Cloud Run nor StackVend checks it; only the generated code can, and QA does not prove that it does. StackVend warns about such a service when the plan is made (`ACCESS.INTERNAL_SERVICE_PUBLIC`): whenever the warning fires, the run pauses for plan approval (gate reason `ACCESS_INTERNAL_SERVICE_PUBLIC`, whatever the plan approval settings, on every run of such a plan), and the plan approval card names the service (past 50 such services it names the first 50 and gives the count of the rest). Approving builds the app as planned, with that service public. The warning names Cloud Run services that a Pub/Sub push subscription in the plan calls and that are neither the app's main service nor called by another service (when the main service is not a Cloud Run service, the first Cloud Run service of the plan counts as the main service and is not named); services that only Cloud Scheduler, Eventarc, Cloud Tasks or Workflows call are not named, because the plan does not record those callers. For an app without browser users, choose **Private: IAM callers only**. Private applies to the whole workload: it makes every service private, including the one browsers use. Otherwise have a person check, in a reviewed change, that the service verifies the token (audience = the one the push subscription sets: the service's URL, or the full push endpoint URL when the subscription sets none; email = the workload's service account). The specification wording "internal ingress" is not detected. Per-service access is planned.
* **QA does not fail a Public app for this.** When QA's reviewer reports that a Cloud Run service of a Public app should accept only some callers (for example only the workload's service account), and the finding belongs to an infrastructure task of the plan, or to no single task and names no file outside `infra/workload/`, the build does not fail at QA or at release and no repair is attempted, because the generated code cannot change it. The QA summary and the pull request's release certificate list the finding as a documented platform limitation (advisory), with the services the plan-time warning named. The same finding still fails the build in a Private workload or when it belongs to an application-code task. When the reviewer's adherence score is below 0.80 and nothing else is listed, QA reports the reviewer as unavailable (no verdict) instead of passing the build.

## Secrets from other systems are added by an operator

The architect's plan says who supplies the value of each Secret Manager secret in it (`initial_value`).

* **A key the app makes and uses itself** (`random`, for example a signing, HMAC or encryption key): with typed infrastructure, the platform stores 64 random letters and digits as the secret's first version in the same deploy that creates the secret. The value never changes on later deploys, a Full Swarm Rebuild or Upgrade IaC, and nothing rotates it. It is stored in clear text in the workload's OpenTofu state (OpenTofu 1.9 has no write-only attributes): the state bucket in the child project on a Per-workload install (readable by the workload's deployer, the Control Center and the child project's owners, editors and viewers, and kept in older object versions), the platform state bucket on a Shared install, and the decommission archive in the platform state bucket. The Cloud SQL and AlloyDB passwords the golden modules generate are kept the same way. The plan JSON the Terraform server returns and stores for a plan run (the Firestore record of a `tf-applier` plan) has every value the engine marks sensitive replaced by `(sensitive value)`; a literal secret written into the workload's own Terraform is not marked by the engine and is not masked (it is in the repository anyway).
* **A database password is not such a secret.** The password of a Cloud SQL or AlloyDB database in the plan is generated by its golden module and kept in that module's own secret; the plan does not list it as a separate secret, even when the specification names one for the database credentials.
* **An existing value is never replaced.** If the deploy finds that a secret marked `random` already exists in Google Cloud with a value (for example a secret of the same name created by hand, which the deploy adopts), it stops before applying anything (`APPLY.SECRET_GENERATION_WOULD_SHADOW_EXISTING`, for an operator) instead of adding its random version over that value; if it cannot read the secret's versions, it stops too (`APPLY.SECRET_VERSIONS_UNREADABLE`).
* **A credential another system issues** (`operator`, for example an API key for a payment provider), **or a secret whose plan does not say**: it is created without a value. This is a warning only: the plan does not wait for approval because of it. The warning (`SECRET.OPERATOR_VALUE_REQUIRED` / `SECRET.VALUE_SOURCE_UNSTATED`) is kept with the run's plan decision, the gateway logs it, and when the plan waits for approval for another reason, the approval card lists the secrets. For now, add the value by hand in Secret Manager (a new version of the secret); until then the app's read fails. A Control Center action to set the value is planned.
* **A secret that already existed is never given a value**, even when a new plan marks it `random`: a version the platform added would become the newest and hide a value an operator may have added. The workload page lists it (`SECRET.EXISTING_NOT_GENERATED`). Add a value in Secret Manager if it has none.
* With agent-written Terraform (not typed infrastructure), no value is generated. A secret the infrastructure declares outside the plan is not named in the warning.

## Some infrastructure code is still written by the AI

New workloads use typed infrastructure by default: the agents describe the infrastructure as a typed list of approved building blocks, and the platform checks it and writes the OpenTofu/Terraform code from it (Settings, *Typed infrastructure (generate mode)*, on unless an administrator turned it off; see [Typed infrastructure](user-guide.md#typed-infrastructure-generate-mode)). The AI still writes the code (HCL) itself, steered toward the [golden modules and bundles](composite-bundles.md) and checked by validators, when:

* the setting is off, or the settings could not be read when the build started;
* the workload was first built with AI-written code (it keeps that path);
* the architect's plan has no typed service topology.

On that path, expect the AI to write some resources directly instead of using a golden module.

* **A resource the platform moves into its foundation module can fail the first plan.** When the AI writes the infrastructure code itself (not typed infrastructure), it can declare a resource at an address that the platform's generated `moved.tf` moves into the foundation module (for example `google_service_account.workload_sa`). That code passes every check and QA, and then the first deploy plan fails with "Moved object still exists". Remove the duplicate resource and use the foundation module's output instead, in a reviewed change.

## Some automatic repair steps can change code that was already valid

Before code is committed, and again before it is applied, StackVend runs repair steps that fix common generation mistakes. Most of the older steps that rewrote code have been removed or now only report what they would change, but a few still rewrite generated Python and infrastructure files even when the input was already valid. At deploy, the committed infrastructure files are applied exactly as written (names, outputs, variable defaults, provider versions, deletion-protection settings, `locals` and the vendored platform modules included), and a deploy never commits anything to the workload repository: the repository always holds what was reviewed. When OpenTofu reports a validate or apply error, the deploy does not rewrite files or guess variable values and retry; the error goes back to the AI, which regenerates the code (one extra generation run per retry, bounded by the retry count).

* In the most recent 27-build test, these steps changed no already-valid input. An earlier run counted 8 such changes, none of which broke a build.
* If a committed file differs from what you expected, check the build logs: repair steps log what they changed.
* **Python package pins can change after QA.** Before the container image is built at deploy, the version pins in a service's `requirements.txt` are aligned to the platform's package list (Settings, *Centrally Governed Package Versions*). This happens after QA ran, so the image can use package versions that QA did not test; the change is logged ("Harmonized requirements") and is not committed to the repository. If a deployed service fails on a package version, pin a version that fits the platform list.
* **A QA repair can add a package in one narrow case.** When QA reports that a service failed to import in its clean install (`PY.IMPORT_FAILED`), the repair may also edit that service's `requirements.txt`, but only by adding new lines, each a package name (extras and a plain version are allowed) that the tested code already names in an import: the import's top-level name, the package the platform's catalog maps it to, or, for an import the catalog does not know, the last part of its path (`google.auth.transport.requests` allows `requests` by an explicit rule). Changing or removing a line, URLs, paths, pip options, markers, a local version (`+x`), `===`, a byte-order mark or a comment declaring an encoding in the first two lines, a package already listed and a package the code does not name reject the whole attempt (`REQUIREMENTS_ADDITION_REFUSED`, in the run's repair events), and the repair limits apply as usual. This is a relation to the code's imports, not a malware check: a name that appears in the path of an import the catalog does not know is accepted if the package index has it, and a package the code never names (such as a database driver chosen only by a connection URL) is refused, with one exception: when QA reports the exact module the import could not find and the platform's package catalog maps it to a package the file does not list, the repair may add exactly that one package, also to a `requirements.txt` the platform created because the generated code had none. A module the catalog does not know is never guessed (the run records `MISSING_MODULE_NOT_IN_CATALOG` with the module name), so add that one in a reviewed change. A repair after a pytest crash may change or remove lines of `requirements.txt` (to re-pin a test plugin), but what it writes must be a plain package name with an optional plain version, and it can only name packages the file already lists, the code imports, or QA's own test tools (`pytest`, `pytest-timeout`, `pytest-asyncio`); a version change of a listed package is allowed, including a downgrade.
* **A test that errors outside its own test function is repaired in the test setup, under the crash rule's limits.** When pytest reports a test as an error rather than a failure (a fixture that fails in setup or teardown, or a test file that cannot be imported), QA reports `PY.TEST_SETUP_ERROR` and the repair may change that service's test setup (`conftest.py`, `tests/__init__.py`, `requirements.txt`) and the errored test files. A `requirements.txt` change follows the crash rule above: it can only name packages the file already lists, the code (tests included) imports, or QA's own test tools. The one exception is the same as for a failed import: when the error was a missing module while pytest collected the test file or set the test up (for example a database driver a fixture loads from a connection URL), QA reports that module, and a package the platform's catalog maps it to may also be added (also to a `requirements.txt` the platform created); a module the catalog does not know is never guessed. A plain test failure (`PY.TEST_FAILED`) is still repaired in the files QA named only.
* **QA does not count skipped tests as passes.** A test that pytest skips (`skip`, `skipif`, a module-level skip) or reports as an expected failure (`xfail`) is counted separately: the QA summary and the release certificate show it as skipped, never as passed. A pass needs at least one test that ran, and a service whose every test was skipped fails QA with `PY.ALL_TESTS_SKIPPED`, which lists the skip reasons (for example a test that only runs when an emulator variable is set). Make such tests run in QA, or add tests that do.
* **QA runs async tests with pytest-asyncio in auto mode.** When a service's test module defines an `async def` test, the platform adds `pytest-asyncio` (at QA's own pinned version) to that service's `requirements.txt`, unless the file already lists `pytest-asyncio` or `anyio`; it is then also installed in the deployed app. QA ignores the workload's own pytest configuration, and whenever `pytest-asyncio` is installed it runs it in auto mode, so every `async def` test and async fixture runs on asyncio, marked or not. A test suite that relies on pytest-asyncio's strict mode, or on anyio tests with a non-asyncio backend beside pytest-asyncio, can behave differently in QA.

## Outdated platform modules are reported, not updated, at deploy

A workload keeps the copy of each platform (golden) module that was committed to its repository. When the platform's module is newer, the deploy applies the committed copy, logs `PLATFORM.VENDORED_MODULE_STALE` and marks the workload **IaC Update** in the Control Center catalog (the **Outdated IaC** filter lists them). To update the module, use **Upgrade IaC** on the workload's page: it opens a pull request that goes through review like any other change.

* A workload under **Code Freeze** (new workloads are frozen by default) cannot receive that pull request: **Upgrade IaC** is refused until an operator clicks **Unfreeze**. Until then an outdated module stays reported and is deployed as committed.
* **Upgrade IaC checks each upgraded file with a Python HCL parser.** The Control Center has no OpenTofu binary, so it parses each upgraded `.tf` file with python-hcl2. That parser rejects some valid HCL, for example an expression inside parentheses whose next line starts with an operator (`? :`, `&&`, `+`, `==`). Such a file is refused with `IAC_PREFLIGHT_PARSER_REFUSED` (not a syntax error: the file is not proven broken) and nothing is committed. The golden modules do not use this style; in a custom module, keep the operator at the end of the line instead. Where an OpenTofu binary is installed, OpenTofu's own parser decides instead.
* **Per-workload installs refuse workload Terraform the platform's parser cannot check.** Before every OpenTofu run on a Per-workload install, the terraform runner reads every Terraform file the run would load with python-hcl2 to check its provider, backend and module settings. A file that parser cannot read is refused even when it is valid OpenTofu (`APPLY.SOURCE_NOT_CHECKABLE`, naming the file and line; OpenTofu's own parser is asked, and a file it rejects too is `APPLY.SOURCE_UNPARSEABLE`). The known case is an expression inside parentheses whose next line starts with an operator (`? :`, `&&`); keep the operator at the end of the line instead. A Shared install only logs these files (`POLICY_WOULD_REFUSE`).

## One region per workload, from the approved list

Each workload deploys into **one** region, chosen on the New Workload form from Settings **Approved Deployable Regions** and kept for the workload's life (it cannot be moved to another region). By default the list holds only the default workload region (`us-central1`), so every workload deploys there unless an administrator adds regions. A workload spread across several regions is not supported. The StackVend platform itself (Control Center, gateway, Terraform server) stays in the region it was installed in; install it in `us-central1`. Workloads created before approved regions have no region of their own and follow the default workload region.

* StackVend never moves a workload to another region on its own. When a workload's region is no longer on the list (`REGION_NOT_APPROVED`), or the list or the workload record cannot be read (`REGION_UNAVAILABLE`), its build and deploy stop for an operator, and budget scale-to-zero does not act on it (it raises the budget-breach approval card instead). Settings refuses to remove a region a workload still uses (`REGION_IN_USE`).
* A Cloud Spanner instance from the `database-spanner` module uses the workload region's regional configuration (`regional-<region>`) when the call passes `region` (typed infrastructure always does). Multi-region configurations (such as `nam3` or `eur3`) and other regions are then refused at plan. A call written without `region` keeps its own `config` as written; only regulated profiles check that location (the compliance plan check).

## GKE workloads: only five placeholders are filled in manifests

When a workload includes Kubernetes manifests (files under a `k8s/` folder), StackVend fills in only five exact placeholders: `${PROJECT_ID}` (the workload's Google Cloud project), `${PRODUCT_ID}`, `${REGION}`, `${SERVICE_NAME}` and `${ARTIFACT_REGISTRY}` (the workload's Docker repository). Everything else, including public images such as `nginx:1.27`, is applied as written. A container image or Workload Identity annotation that still contains `$` after that (for example `${IMAGE}`) stops the build with `K8S.PLACEHOLDER_UNRESOLVED` instead of being guessed.

The deploy applies the manifests to the workload's GKE cluster right after the OpenTofu apply, in the `default` namespace unless a manifest names its own, with a server-side dry run of every manifest first. Cluster-wide kinds (for example `ClusterRole`), kinds the cluster does not serve, and system namespaces such as `kube-system` are refused.

* **Namespaces.** StackVend creates each namespace the manifests name (a manifest's `metadata.namespace`, or a `Namespace` manifest) before the dry run, if it does not exist yet; an existing namespace is never changed. A `Namespace` manifest may hold only `apiVersion: v1`, `kind`, `metadata.name` and the standard `app.kubernetes.io/` labels `name`, `instance`, `version`, `component` and `part-of`; StackVend adds `app.kubernetes.io/managed-by: stackvend`. Any other field, label or annotation in it (for example a Pod Security label) is refused before anything is applied and goes back to the developer agent for its bounded repair. A system namespace is refused for an operator, and StackVend never creates a namespace whose name starts with `kube-`, `gke-` or `gmp-` (reserved for Kubernetes, GKE and Google Managed Prometheus). A declared label is not added to a namespace that already exists (the deploy report says `labels_applied: false`). When the manifests cannot be applied, the deploy fails with `K8S_MANIFEST_APPLY_FAILED` and lists each manifest's result; it is never reported as deployed. A manifest the cluster rejects as invalid on the dry run goes back to the developer agent for its bounded repair; any other failure (permissions, cluster not reachable, a refused kind or namespace, a field conflict) stops for an operator.

## GKE clusters use the project's default network

A GKE Autopilot cluster that StackVend creates for a workload runs on the workload project's `default` VPC network, with private nodes (no external IP addresses) and the pod and service IP ranges GKE allocates itself. StackVend does not create a dedicated subnet, secondary IP ranges or Cloud NAT for it yet (a dedicated GKE network is planned for a later release), and a workload's typed infrastructure (`infra/workload/iac_intent.json`) cannot declare networks, subnetworks, routers, Cloud NAT or firewalls: the network is the platform's.

* Without Cloud NAT, pods cannot reach internet addresses outside Google Cloud. StackVend does not configure Private Google Access on the subnet itself; GKE manages it for clusters with private nodes.
* When the folder's organization policy `constraints/compute.skipDefaultNetworkCreation` is enforced, the project has no `default` network and a GKE workload cannot be deployed yet: the OpenTofu apply of the cluster fails and the deploy stops with that error.
* **QA does not fail a GKE workload for this.** When QA's reviewer reports a dedicated subnet, secondary ranges or Cloud NAT missing for an infrastructure task of the plan, the build does not fail at QA and no repair is attempted, because the workload's infrastructure cannot change it. The QA summary lists the finding as a documented platform limitation (advisory).
* This applies only when the platform's root module gives the cluster the `default` network. A workload whose own root-module file passes the cluster another network is judged as before.

## Workload infrastructure cannot grant privileged IAM roles

StackVend's IAM policy refuses a fixed set of privileged roles in a workload's infrastructure, for any member and on any resource: `roles/owner`, `roles/editor`, `roles/iam.securityAdmin`, `roles/iam.serviceAccountAdmin`, `roles/iam.serviceAccountTokenCreator`, `roles/resourcemanager.projectIamAdmin`, `roles/resourcemanager.folderAdmin`, `roles/resourcemanager.organizationAdmin`, `roles/run.admin`, `roles/artifactregistry.admin` and `roles/cloudbuild.builds.editor` (see the [threat model](threat-model.md), "Forbidden resources and roles"). Neither the typed infrastructure file (`infra/workload/iac_intent.json`) nor Terraform written for the workload can grant one; the gate refuses it before anything is committed.

* A workload needs none of them for identity tokens: a Cloud Run service gets its own identity tokens from the metadata server, and Cloud Scheduler mints a job's OIDC token for the job's service account through its own service agent.
* A feature that does need one (for example signing URLs as the workload's own service account, which needs `roles/iam.serviceAccountTokenCreator` on it) cannot be built yet.
* **QA does not fail a workload for this.** When QA's reviewer reports one of these roles missing for an infrastructure task of the plan, and names the exact role, the build does not fail at QA and no repair is attempted, because the workload's infrastructure cannot grant it. The QA summary lists the finding as a documented platform limitation (advisory). A finding about any other role is judged as before, and any other missing grant, resource or setting of the same plan task is still reported and repaired. The architect is also told which roles are refused, so its plans should not ask for them; a plan that genuinely needs one says so in its risk assessment.

## Cost estimates are approximate

The cost estimate shown before a build is **approximate**: it prices the kinds of compute services and resources in the architect's design from a fixed price table, not the actual Terraform plan. Use it as a rough signal only, and keep budgets and billing alerts in place. When the estimator is unavailable or not configured, or the design has a compute kind it cannot price, the build asks for an operator approval instead of passing silently.

## No billing budgets are created for workloads

StackVend does not create a Cloud Billing budget for a workload. The budget warnings and the breach policy you choose for a workload (for example scale to zero) act only on Cloud Billing budget notifications, so they never trigger on their own: **budget enforcement stays inactive for a workload until a budget exists for it.** Automatic budgets are planned for a later release. If you create a budget on this install's billing account named `budget-<workload id>` (or one whose id is recorded on the workload) and connect it to the `billing-budget-alerts` Pub/Sub topic, the breach policy acts on its notifications within about 30 minutes: the `billing-alert-drain-job` reads the topic every 30 minutes. A workload's breach is enforced once per billing month and threshold; re-sent notifications do not act again. To record spend and warnings without enforcing, set `billing_breach_enforcement_enabled = false` (see [Configuration](configuration.md)).

A budget cap written in a specification (for example "a $10.00 FinOps budget cap") is therefore not built into the workload's code or infrastructure. It is met by the workload's **monthly budget ceiling**, the amount given when the workload is created (or the platform default). When QA's reviewer still reports a missing Cloud Billing budget for an infrastructure task of the plan (or for no single task), the build does not fail at QA or at release: the QA summary and the release certificate list the finding as "Satisfied by the platform" with the recorded ceiling. This needs a ceiling of at least $0.01; otherwise the finding fails the build as before. A reviewer adherence score below 0.80 with nothing else listed is reported as an unavailable reviewer (no verdict), never as a pass. StackVend does not compare the ceiling with the amount in the specification, so check it on the workload page and change it there if needed.

Approving a budget-breach card with **Restore** or **Increase budget** runs the FinOps enforcer job and waits for it, which can take up to 10 minutes. The page may show a network error before then while the restore still completes. Deciding the card again is safe: a workload that is already restored is left unchanged, and a restore that failed or only partly completed says which resources were not restored. A restore is reported as done only after Cloud Run services, VMs and Cloud SQL instances are read back with their pre-quarantine settings; a Cloud SQL instance that takes longer than about 3 minutes to start is reported as not confirmed yet, and deciding the card again checks again. GKE node pools are not read back, and they are resized to the size they were created with, not the size they had before the quarantine. A breach on a workload that is already quarantined or has its billing detached changes nothing, even when the ceiling or the Circuit Breaker % changed. Deploying a quarantined workload again does not clear its quarantine: until it is restored from its budget card, a new breach changes nothing even though the redeployed services run.

## Running workloads are not repaired automatically

Automatic repair of running workloads (SRE auto-healing) is off in this preview. Errors inside workload projects are not sent to StackVend's error sentinel, and the sentinel starts no repair runs; the per-workload **SRE auto-healing** switch has no effect yet. Watch your workloads with Cloud Logging and Cloud Monitoring, and start a fix yourself with a feature request or a retrigger.

The workload page's log stream reads two sources: the workload's own runtime logs (Cloud Run, GKE, VM and function logs in its child project) and the platform pipeline's logs about it (the host project, entries tagged with exactly this workload). Project vending gives the Control Center's service account read access to logs (`roles/logging.viewer`) in each child project it vends. For workloads vended before that change, an administrator runs the backfill once: `POST /api/settings/cc-log-reader/backfill` in the Control Center (send `{"dry_run": true}` to list what it would grant). Until then such a workload's first source shows **Workload project logs unavailable (PERMISSION_DENIED)** and only the platform pipeline logs (marked *platform pipeline*) are listed. The workload source lists every runtime log in the child project, which is the workload's own while one child project holds one workload. A source that cannot be read is always shown as unavailable, never as "no logs"; when neither can be read the page shows `LOGS_UNAVAILABLE`.

## Helm charts

Tool-server actions that need an administrator's approval (Helm uninstall, Agent Engine deploy, Discovery Engine datastore create) do not run by themselves after the approval: the approval card shows a single-use approval id, and whoever called the tool must call it again with that id within 15 minutes.

The Kubernetes tool server does not install Helm charts in a default install. Its Helm tools are included, but no Helm version is pinned, so every Helm call answers `HELM_UNAVAILABLE`. It applies plain Kubernetes manifests and reads status, logs and events. Deploy charts yourself if a workload needs them.

## Permissions that the installer cannot grant for you

Some features need organization or billing roles that the person running the installer may not have. The install still succeeds without them; the feature stays off and the Control Center **Settings** page shows what is missing and how to fix it.

* **Billing.** Three grants on the billing account need a *Billing Account Administrator*: *Billing Account User* for two StackVend service accounts (vending links each new child project to billing; the FinOps enforcer re-links billing after a budget quarantine) and *Billing Account Viewer* for the Control Center's (the Settings billing card). Terraform makes them only when the person running the installer or `scripts/apply.sh apply` is a Billing Account Administrator. Until they exist, a workload run stops at project vending with `BILLING_NOT_LINKED`, re-linking after a quarantine fails, and the Settings billing card shows a warning with the exact commands (see [Post-install: billing access](quickstart.md#post-install-billing-access)).
* **No external VM IPs.** StackVend sets the organization policy `compute.vmExternalIpAccess` = deny all once on the managed-workloads folder, so every project in it inherits it. That needs an *Organization Policy Administrator* (`roles/orgpolicy.policyAdmin`, which Google allows only on the organization) running the installer or `scripts/apply.sh apply`; no StackVend service account gets an org-policy role. Without it the installer prints a warning with the grant command and skips only this policy: VMs in vended projects can then get external IP addresses, and each vend records `VENDING.ORG_POLICY_NOT_ENFORCED` with the fix in the workload's `org_policies` record (the Settings page does not show this one). Grant the role and run `scripts/apply.sh apply` again. Note that the policy covers **every** project in that folder, including projects you put there yourself, and that a project-level policy or a child vended into another folder can still allow external IPs (the vend record then says `NOT_ENFORCED`). With the policy in place, a workload whose resources need VMs with external IPs can fail to deploy; the golden `orchestration-composer` module creates a Cloud Composer 2 environment with public IPs by default, whose nodes are such VMs.

## Every workload uses one Google Cloud project: the project quota

Every workload is deployed into its own child project, and StackVend's project-vending service account (`sa-project-provisioner`) creates it. Google limits how many projects an account can create; inside an organization, Google checks both the creating account's quota and the organization's, and the project is created when either has room. A project that is pending deletion still counts toward the quota until Google deletes it for good, about 30 days after it was shut down. Decommissioning a workload shuts its project down, so **decommissioning does not free quota at once**: the slot comes back about 30 days later. Redeploying a workload into a fresh project uses one more.

* **What you see.** A run over the quota stops at project vending (stage `vending`) before anything is created, with the error class `VENDING.PROJECT_QUOTA_EXCEEDED`. Google reports the exhausted quota in the project-creation operation (status code 8, `RESOURCE_EXHAUSTED`, or a `QuotaFailure` detail), and StackVend recognizes it from either of those fields. The message names the project it tried to create, says the quota belongs to the creating account and the organization, and points here. Any other refusal shows Google's own error.
* **Raising the quota.** In the Google Cloud console open **IAM & Admin ▸ Quotas & System Limits**, select your organization, filter on the metric `cloudresourcemanager.googleapis.com/projects_count` (Cloud Resource Manager API), choose **Edit quota**, and enter the new value with a short reason. Google reviews the request; see [Creating and managing projects](https://cloud.google.com/resource-manager/docs/creating-managing-projects) for its project quota rules. Plan for the workloads you will keep plus the projects decommissioned in the last 30 days.
* **A second, separate limit:** the number of projects linked to one billing account. A vend over it stops with `BILLING_NOT_LINKED`, and the message names that quota and links to Google's billing quota increase request.

## GitHub Actions deploy of a workload (preview)

While a GitHub workload's **GitHub Actions Deploy** switch is on (the default), the generated `.github/workflows/deploy-<service>.yml` builds and deploys the code that people push to the workload's branch (the Day-2 path; see also [Other security gaps in this preview](#other-security-gaps-in-this-preview)). StackVend's own runs deploy through its pipeline, not through this workflow.

* **StackVend's merge commit starts no workflow.** When StackVend merges its pull request into the workload's branch (the automatic release merge, or the merge after you approve the change in the Control Center), the merge commit's message ends with GitHub's `[skip actions]` directive, because StackVend builds and deploys that commit itself. GitHub then starts no `push` workflow for that one commit, including your own CI workflows in the repository; runs on the pull request before the merge are not affected, and every later push runs all workflows as usual. Serverless Git workloads have no workflows and are unchanged.
* **A push before the first deploy finishes fails at Google sign-in.** The first deploy creates the workload's identity federation pool and the deployer account. A person's push to the branch before that deploy has finished (for an approved change, this includes the time the run waits for the approval) gets a failed run at `google-github-actions/auth` with `invalid_target`. Run the workflow again after the deploy has finished.
* **Approve StackVend's pull request in the Control Center, not on GitHub.** Merging it on GitHub yourself starts the deploy workflow: before the first deploy it fails at Google sign-in, and on a re-run of an existing workload it deploys alongside StackVend's own deploy.
* **A run that ends after the merge deploys nothing.** When a run stops after StackVend's merge (stopped by you, a budget stop, or an approval callback that expired), neither StackVend nor the workflow deploys that commit. Start the deploy workflow by hand (**Run workflow** on the workflow's page in GitHub's **Actions** tab, `workflow_dispatch`) or run the workload again.
* **Cloud Run: the access flag of the deploy step.** The Cloud Run workflow passes `--allow-unauthenticated` or `--no-allow-unauthenticated` to `gcloud run deploy`, but the deployer account (`sa-gh-deployer`) has `roles/run.sourceDeveloper`, which cannot change a service's IAM policy. The step may therefore report an error or a warning about the service's IAM policy after the new revision is deployed (not yet verified on a live workload). Who may call the service is set by StackVend's Terraform; the flag does not change it.
* **GKE: the workflow deploys no new code.** The GKE workflow builds no container image: it only applies a top-level `k8s/` folder when the repository has one. A push that changes the app's code therefore finishes green without deploying it. Deploy a code change to a GKE workload by starting a run from the Control Center.

## Other known issues

* **Long specifications lose detail.** Results are best with a specification of up to about 25,000 characters (roughly 8-10 pages). Above that the architect splits the specification into parts by its headings, plans each part separately and merges the plans. The lead developer reads only the first 40,000 characters of the specification, next to the architect's task plan. The developer agents and the QA review work from the plan, not from the specification, so a detail that the plan does not carry is neither built nor checked. A very large document (over about 100,000 characters) may fail to process: the whole specification travels in the workflow's arguments, which Cloud Workflows limits in size, so the run may fail to start. The New Workload form shows the size guidance and a live character count; it warns but does not refuse a long specification.
* **A very large service can run out of automatic QA repair.** QA repair asks the AI to rewrite each affected file in full, and one AI answer has an output size limit. When the files of one service that need repair are larger than one answer can hold (for example several large modules together), the repair cannot fit, the repair time budget runs out and the run ends `FAILED` with the error class `CODE_DEFECT` and nothing deployed. The branch and pull request are kept. Splitting the specification into smaller services, or resubmitting, avoids it.
* **Plans with a virtual machine may show a network step the platform does not build.** When a plan includes a Compute Engine worker and your organization forbids external IP addresses on VMs, the compliance stage reports a policy conflict, requires plan approval, and adds a plan step and plan text about a custom VPC, Cloud NAT and SSH firewall rules. The platform does not build that network: workers use the platform network without an external IP, which already meets the policy. Approve the plan to continue; nothing extra is created.
* **A deploy or vending job that is killed before it reports keeps its build slot until the workflow's wait ends.** The workflow waits up to about 24 hours for the tf-applier job's answer and 20 minutes for vending's. An answer the job produced but could not deliver is kept and sent again while the workflow still waits (by the next build submission when every build slot is taken, or by the Flight Deck), so the run goes on. A job that is stopped before it produces an answer (out of memory, a hard kill after it started the deploy) leaves nothing to send: the run ends `DEPLOY_TIMEOUT` (or `GATE_TIMEOUT` for vending) when the wait ends, and the build slot is held until then. Abort the run to free the slot sooner.

* **Golden Cloud SQL and AlloyDB modules.** Both need a private network with Private Services Access (`private_network_id` / `network`) and refuse a missing one at plan time (Cloud SQL only when `enable_public_ip` is also off, which typed infrastructure always keeps). With typed infrastructure the platform supplies the network; with agent-written Terraform the agent must pass one (for example the `networking-vpc` module's `network_id`).
* **Golden `security-secret` module.** It works as a child module but fails as a root module.
* **Deletion protection.** Golden data-store modules turn deletion protection on by default. Data stores that the AI writes directly may still be created without it. Cloud Run services and jobs that the AI writes directly are applied with the deletion-protection value they were committed with (when the argument is absent, the Google provider's default applies); StackVend no longer turns it off at deploy, so a redeploy that would replace such a protected service or job stops before apply as a blocked destroy for an operator to decide (the Google provider would refuse it too) until the code sets `deletion_protection = false`. AlloyDB is not covered: the pinned Google provider (6.35.0) has no deletion-protection setting for AlloyDB clusters, so the golden `database-alloydb` module cannot turn it on; with **Require Human Approval for Destructive Terraform** on (the default), an Agent-mode deploy that would delete or replace an AlloyDB cluster or instance still stops for an operator.
* **A failure while applying is not sent back to the AI.** OpenTofu names the failing file only for errors it finds before anything is applied (validate and plan). An error during the apply itself (a cloud API refusing a resource, a quota, a permission, a container that does not start) has no such location, so the run stops with `DEPLOY_FAILURE_UNATTRIBUTED` and the engine's error instead of asking the AI to rewrite the code. Read the error in **Flight Deck**; relaunch with Fast-Path Deploy when the cause was outside the code, or with a full build when the code must change.
* **`prevent_destroy` failures have no error class.** When workload Terraform marks a resource `prevent_destroy` and a change would destroy it, OpenTofu refuses the plan and nothing is changed, but the deploy fails without a specific error class and is not routed to an operator as a blocked destroy. Read the deploy log in **Flight Deck**; to go ahead, remove the setting in a reviewed change.
* **Custom Git bundles.** Bundles can be registered only from github.com repositories, and they are read with the platform's own GitHub access: a bundle's own access token setting is not used yet, so a private repository the platform cannot already read cannot be used. A bundle's content is not policy-checked when you register it, only at apply time like any workload Terraform; register bundles only from repositories you trust.
* **Platform services other than the Control Center are internal-only.** With `host_internal_ingress = true` (the installer writes it, so a new install is internal-only from its first apply), a request to any other platform service from outside the platform is refused with HTTP 404 before IAM is checked, so operators cannot `curl` them with an ID token or use `gcloud run services proxy`; use the Control Center and Cloud Logging, or the break-glass steps in [Configuration: Platform network](configuration.md#platform-network-internal-only-host-services). The Serverless Git clone URL that the Control Center shows works only from inside the platform (people were already refused by the git server itself). An existing install already on the platform network turns it on with one `scripts/apply.sh apply` after setting the variable; one not yet on the network takes two (network first, then ingress). Turning `host_vpc_egress` off again after it was on can take a second apply a few hours later: Cloud Run releases the network addresses of old revisions with a delay, and the subnet cannot be deleted before that. The subnet (a `/24`) is sized for the platform's own services and jobs at their maximum instance counts with headroom for revision rollouts; it has not been measured under load (a larger `host_egress_subnet_cidr` is one apply). The first network apply enables Cloud DNS and Service Directory and uses them in the same run, so it can fail once while the APIs propagate: run the same apply again. After a failed apply, re-run `scripts/apply.sh apply`, not `scripts/bootstrap.sh`: bootstrap's check that ingress waits for the network looks at the subnet only, not at every service having joined it.
* **In-product upgrade: services and jobs only, after console approval.** Settings ▸ Upgrades ▸ **Update StackVend** deploys a newer signed release's services and jobs once the upgrader is installed. By default every such build waits until an administrator approves it in the Google Cloud console (Cloud Build ▸ History): pressing the button alone deploys nothing. The approval must come within 60 minutes of the request; a build approved later refuses to start, and a build nobody approves keeps the upgrade lease and maintenance mode until that window has passed and an administrator clears it (**Clear the stale lease**). It never installs a release that changes platform Terraform, and before the public release there is no release to install (the official repository reads "not published yet"). **On `0.9.0-preview` and `0.9.1-preview.1` the button cannot update at all:** it asks GitHub for the release tag in a form GitHub does not answer, so every press stops with `TAG_UNRESOLVED` and changes nothing (no lease, no maintenance mode). Those installs update with `scripts/upgrade.sh <tag>` (below); the button works on an install that already runs `0.9.1-preview.2` or later, for the releases after it. Approve only a build whose `_REQUEST_ID` substitution matches a request you just made (find it in Cloud Build ▸ History by that substitution; the card links Cloud Build ▸ History; its link to this build appears only once the build starts, after approval). After the **first** button update, do not use **Roll back services**: jobs cannot be rolled back yet (`ROLLBACK_UNAVAILABLE`, the result is partial); go back with `scripts/upgrade.sh <previous tag>` instead. For those, and on installs without the upgrader, upgrade from a terminal in the checkout you installed from: `PROJECT_ID=<id> bash scripts/upgrade.sh <tag>` fetches the release tag, verifies its SSH signature against `scripts/release/allowed_signers` of the checkout you installed from (never the release's own list; an unsigned tag, a lightweight tag or another key is refused unless you pass `--trust-unsigned`, which prints a red warning; a checkout without that file is refused the same way), from `0.9.1-preview.2` on refuses an annotated tag whose own name is not the tag you asked for (`UPGRADE_TAG_NAME_MISMATCH`: an older signed release published under a newer name; also with `--trust-unsigned`; on `0.9.0-preview` and `0.9.1-preview.1` the `upgrade.sh` that runs has no such check, so before running it check the tag yourself: `git fetch --no-tags <remote> refs/tags/<tag>:refs/tags/<tag>`, then `git cat-file tag refs/tags/<tag> | sed -n 's/^tag //p'` must print exactly the tag, and `git -c gpg.format=ssh -c gpg.ssh.allowedSignersFile=scripts/release/allowed_signers verify-tag refs/tags/<tag>` must pass with the `allowed_signers` of the checkout you installed from; never pass `--trust-unsigned` for an official release), checks it out (detached; your branch is not moved), shows the read-only `apply.sh plan`, asks you to confirm, runs `apply.sh apply` and then `deploy-services.sh --all-jobs`, and ends with a read-only smoke check of the platform's Cloud Run services. It refuses a working tree with changes and a target that does not match its vars file, and every stop (also Ctrl-C) prints one next command. The release's own scripts run, with your credentials, for the read-only plan before you confirm, which is why the signature is checked first; it also prints the release commit and tagger. With `--trust-unsigned` nothing is verified: use it only for a repository you trust. It does not check that the tag is newer than the installed release: a downgrade to an older release under that release's own name runs the same way (the plan shows every change and the destroy gate still applies; the smoke check can then report `SMOKE_STAMP_MISMATCH` when the older release leaves the newer stamp in place). In a fork, `origin` has no release tags: add the official repository as a remote and pass `--remote=<name>`; upgrade.sh then applies the upstream release, not your fork's `main`. Without it, verify the tag before anything of it runs, from a clean checkout of the one you installed from: fetch it (`git fetch --no-tags origin refs/tags/<tag>:refs/tags/<tag>`), check that `git cat-file -t refs/tags/<tag>` prints `tag` and `git for-each-ref --format='%(tag)' refs/tags/<tag>` prints the same tag, and run `git -c gpg.format=ssh -c gpg.ssh.program=ssh-keygen -c gpg.program=false -c gpg.openpgp.program=false -c gpg.x509.program=false -c gpg.ssh.allowedSignersFile=scripts/release/allowed_signers verify-tag refs/tags/<tag>`; only then `git checkout --detach 'refs/tags/<tag>^{commit}'`, `scripts/apply.sh apply` when files under `infra/platform/` changed, and `scripts/deploy-services.sh`; see the release's `CHANGELOG.md` entry for the order (the README's "Updating an installation" has the same steps as commands).
* **Upstream sync workflow.** `.github/workflows/sync-upstream.yml` is **off by default**. The workflow always syncs into, and opens its pull request against, the repository's default branch, also when a manual run is started from another branch. To enable weekly upstream sync in a fork, set the GitHub repository variables `STACKVEND_UPSTREAM_REPO` (for example `gh variable set STACKVEND_UPSTREAM_REPO --body example-org/stackvend`) and `STACKVEND_UPSTREAM_SYNC` (`gh variable set STACKVEND_UPSTREAM_SYNC --body true`). When enabled, the workflow reads the upstream without credentials (a private upstream stops the run with `SYNC_UPSTREAM_FETCH_FAILED`), and it is tag-based (it targets the newest `vX.Y.Z` release tag from upstream tags, never `main`, and ignores pre-release tags), verified from `0.9.1-preview.2` on (it merges only an annotated tag whose own name is that tag, signed with SSH by a key in `scripts/release/allowed_signers` of the repository's default branch; anything else stops the run with one error naming the tag and the manual path, nothing is pushed, and one unsigned higher tag upstream stops the sync until it is removed there) and PR-only (it pushes only its `chore/sync-upstream-vX.Y.Z` branch and opens a pull request; it never pushes to `main` or auto-merges). Each pull request body states `needs apply.sh: yes` or `needs apply.sh: no` (with the matching paths), lists every changed trust-anchor path (chosen by shape: scripts, workflow files, the release keys, the upgrader, any dot entry at any depth, every Markdown file outside `documentation/`, build and test configuration, every non-ASCII path) and the tag's signer, and points to `CHANGELOG.md` for the upgrade run order. **The workflow of releases up to `0.9.1-preview.1` does none of this verification** and its pull request body does not show changed scripts or release keys; scheduled runs use the workflow on the default branch, and the sync ignores pre-release tags, so no fork gets the verified workflow through the sync. Until the default branch holds it, merged by hand after the checks of the README's "Opt-in upstream sync" (`git cat-file -t`, the `%(tag)` name check and `git verify-tag` with the flags above), keep `STACKVEND_UPSTREAM_SYNC` set to `false`, delete the token (`gh secret delete STACKVEND_SYNC_TOKEN`), and do not merge a sync pull request opened by the old workflow without the same checks. Sync pull requests must be merged with a **merge commit** (not squash or rebase) so the upstream tag commit remains an ancestor of `main`. Closing a sync pull request without merging it skips that release until a newer one is published (reopen the pull request to take it). With the default `GITHUB_TOKEN`, sync pull requests do not trigger other GitHub Actions workflows (CI) — re-run CI or push a commit on the branch before merging — and releases that change `.github/workflows/**` cannot be pushed. Both limits exist because GitHub keeps that token from starting more workflow runs or changing workflow files. The optional repository secret `STACKVEND_SYNC_TOKEN` (a token with write access to Contents, Pull requests and Workflows) removes both, and with it the pushed branch's workflow files, which come from upstream, run in your repository with its secrets; add it, if at all, only after the verified workflow is on the default branch (it then uses the token only in the push and pull-request step). Without it, merge such releases by hand, verified the same way.
* **A change pushed to the workload's branch during a build stops the build if the build would overwrite it.** A build reads the repository when it starts and commits its files onto the branch's latest code at the end. When someone changed, added or deleted a file on the workload's branch in the meantime (or before a QA repair of that build) and the build would write or delete that same file, nothing is committed and the run ends `MAIN_MOVED` (reason `BASE_BRANCH_MOVED`, with the files named): re-run the workload so the build starts from the current code. Changes to files the build does not write are kept. A commit made before this check existed is not checked when QA repairs it (`BASE_SNAPSHOT_UNAVAILABLE` in the log), and the deterministic **Upgrade IaC** commit is not checked.
* **A relaunch keeps some of the earlier build's unused files.** A build records the application files it wrote (`workloads/<id>.app_provenance`: the path and the SHA-256 of every version the platform committed there, on any branch, merged or not; at most 16 versions per path). The next full build of the whole application (not a one-turn change and not a repair of a failed QA or deploy, which delete nothing they did not write themselves) deletes, in its own commit, the recorded Python files it no longer writes, when their content is exactly one of the recorded versions, no file that stays imports them (any folder of the repository counts as an import root) and no file that stays names them exactly (a string in Python code, or a word of any other file that stays, such as a Procfile, Terraform file, Makefile, `.env` file or notes; a path matches by its last folders and file name, and `python -m <package>` names the package's `__main__.py`). A module name built only at run time (an f-string) is not seen, so such a module can be deleted. It keeps everything else: files a person changed or added, files of builds made before this record existed, files that are not Python (templates, data, notes), `conftest.py`, a package `__init__.py` whose folder still has files, Alembic migrations (`alembic.ini` `script_location`, or a folder with `env.py` and `script.py.mako`), every file in a build that could not read the whole repository, and every file in a build where a remaining Python file does not parse or uses a dynamic import (`importlib`, `pkgutil`, `__import__`, `exec`, `eval`, `runpy`, `import_string`). Two dynamic imports do not stop the clean-up: `__import__("x")` or `import_module("x")` with one fixed module name counts as an ordinary import of `x`, and one whose name starts with fixed text (`import_module(f"plugins.{name}")`) keeps every module whose name could start that way. A QA failure in a kept file is not repaired in place (the QA repair edits only the files the tested build wrote). When that file is the same on the default branch and no new build could remove it, the run stops with `OPERATOR_ACTION_REQUIRED`, reason `QA_FINDING_ON_UNOWNED_FILE`, naming the file and why: at once for an earlier build's file the clean-up keeps, or for a finding about the file itself (not a test result), and otherwise (a test that fails in a person's file, a changed file or a file with no record, which the build's own change may have broken) only after one rebuild, when the same file fails again; delete or fix such a file in a reviewed change. A QA failure in a file the platform renders on every run (the Terraform files it renders, the generated `.github/workflows/deploy-*.yml` files, `cloudbuild.yaml`, the Python version pin) stops the run with `PLATFORM_DEFECT`, reason `QA_FINDING_ON_PLATFORM_RENDERED_FILE`, because no developer change can fix it; the stop names what the file is rendered from (the architect's service topology, the platform's tables and templates, the compliance decision, network facts, the AI's typed intent) and says whether the failure is a platform capability gap or an architect/topology issue. The one exception is `infra/workload/custom.tf.json`, which the platform renders only from the AI's typed intent `infra/workload/iac_intent.json`: a QA failure there is repaired through the intent. The developer's answer lists the deleted files (`app_orphans_deleted`) and `pipeline_executions/<trace>.stages.developer.app_orphans` records the decision.
* **A full rebuild of a deployed workload can rename its resources.** **Full Swarm Rebuild** designs the workload again, and the new design can name a resource differently (for example a Pub/Sub topic). OpenTofu then plans to delete the old resource and create the new one. When that would delete or replace a resource that holds data, the deploy stops with `DESTROY_REQUIRES_APPROVAL` and nothing is applied: change the workload so the plan keeps the resource, or approve the deletion as the message describes. Use **Fast-Path Deploy** to redeploy without a new design.
* **A new private app can refuse you for a few minutes after its first deploy.** A workload that is private behind Identity-Aware Proxy grants its listed people access during the deploy, and Google takes a few minutes to apply that grant. Until then the app answers "You don't have access" even for a listed person. Wait a few minutes and reload; the workload's page already shows it as deployed.
* **A fixed ID-token audience between two Cloud Run services.** When one generated Cloud Run service calls another and the called service's own code verifies Google ID tokens against one fixed audience (for example `https://service-b.orders.example`), the caller's `<CALLEE>_AUDIENCE` holds that same value; otherwise it holds the called service's URL. A fixed audience works only when Cloud Run does not enforce invoker authentication on the called service (a public workload, the service verifies the token itself), so on a private workload the caller always gets the URL: Cloud Run's own check accepts only the service's URL as the audience, because the golden `compute-cloudrun` module exposes no `custom_audiences`. The fixed audience is read from a module-level constant, or from the default of an environment read (`os.getenv("NAME", "https://...")` or `os.environ.get`). The default is used only when all of these hold: the platform sets no variable with that name on the called service; the service's own code does not set it (no write to that name, no `dotenv`, no `.env` file); its Procfile starts a known server directly, with no variable assignment, no shell script and no `-e`, `--env`, `--env-file` or `--config` option; and no variables file or Terraform override in the repository can change the service's environment variables. The check reads the repository the build deploys, including files the build does not rewrite. Otherwise the caller gets the URL. A library that sets environment variables by itself when the service starts is not detected. When several services verify the same fixed audience, a token minted for one of them is accepted by all of them. An audience read without a default, or from a settings field or a parameter default, is not used either: the caller gets the URL.
* **Environment variables the platform does not set are a warning, not a stop.** Before commit, each Cloud Run service's generated code (test files excluded) is read for `os.getenv("NAME")`, `os.environ.get("NAME")` and `os.environ["NAME"]` with a fixed name. A name the platform does not set on that service (its edge and resource bindings, the Cloud Run module's own variables such as `PROJECT_ID`, Cloud Run's `PORT` / `K_SERVICE`) is listed on the workload page under **Environment variables the platform does not set**, with the file, the line and the default the code falls back to. The build is not stopped and nothing is repaired: QA mocks the cloud, so such a read usually shows only in the deployed service (for example a project id read from `GCP_PROJECT` that falls back to `"local-project"`). Some entries are intended optional settings (`LOG_LEVEL`, `DEBUG`). At most 50 entries are kept per build (20 per service), with the total shown. Not checked: GKE and Compute Engine services (the page says their variables are not known), a workload whose variables files or Terraform overrides may change the service's variables, names built at run time, pydantic settings classes, and variables a Procfile, `.env` file or library sets.
* **Spot batch workers are deleted after 24 hours.** A GCE worker that runs on Spot capacity gets a maximum run time of 24 hours from its instance template, and Compute Engine deletes the VM when it is reached. A specification cannot change the limit yet. Standard (non-Spot) workers have no limit. A launcher that sends its own `scheduling` settings when it creates a VM from the template replaces the limit, and a VM that powers itself off is stopped, not deleted.
* **A stage job that is stopped does not resume.** The architect, developer and QA stages each run as one execution of the `stage-runner` Cloud Run Job (budgets 30, 60 and 45 minutes). If that execution is stopped (its task timeout, a cancel, or a crash such as running out of memory), the stage stops, nothing is committed after that point, and the run ends `STAGE_INTERRUPTED` (at once on a stop Cloud Run announces, otherwise within about five minutes); finished developer tasks are not reused. Re-run the workload. Each stage job also waits for its execution to start (usually under a minute); that time counts against the stage's budget.
* **The build queue moves only on an event.** A queued build starts when a running build reports its end, when a new build is submitted (the admission then also asks Cloud Workflows whether the builds holding the slots are still running, and frees the slot of one whose workflow has ended), or while someone has the Control Center's Flight Deck open (each refresh does the same check). Nothing runs on a timer: if a build's workflow ends without reporting it and nobody submits a build or opens the Flight Deck, the queued builds wait until one of those happens. A scheduled check needs a platform Terraform change and is planned for a later platform release.
* **Builds wait for a build slot, also after an approval.** Only **Max Concurrent Builds** (default 1) builds that use the AI models run at once; the rest wait in a queue. A build waiting for a person (a plan, quota or pull-request approval) gives its slot to the next queued build; when it is approved (or sent back for rework) it takes a slot again, and when none is free it waits at the head of the queue, ahead of new submissions, and goes on when a slot frees. So an approved build can wait before it goes on, and the time it waits for a slot counts toward the workflow's 24-hour approval wait. Builds started by the refactor scanner or SRE remediation always wait for a plan approval, so they hold no slot while nobody decides. Builds that were already running when this limit was installed hold no slot, so right after the update up to the limit of new builds can start next to them. The limit counts whole builds, not individual model calls.
* **A workload waiting for an approval shows as Provisioning.** While a run waits for a person (a plan, cost, quota or pull-request approval card), the Workloads Catalog and the workload's page keep showing the workload as Provisioning; there is no separate "waiting for approval" status yet. Open **Approvals** to see what the run waits for (the run's current stage in **Flight Deck** also says so for plan and pull-request approvals). An approval nobody decides ends the run after the workflow's 24-hour wait.
* **Infrastructure entries deleted by a QA repair are not listed in the Control Center.** When the QA reviewer names entries of the typed infrastructure file (`infra/workload/iac_intent.json`) that must be deleted, and the repair deletes them, the Control Center does not list the deleted entries yet; read them in the repair's commit in the workload's repository.
* **Internal names.** Many internal resource names still use the original `castor` prefix (service accounts, buckets, secrets, scheduler jobs, some variables). They will change in a later release for new installs only.
