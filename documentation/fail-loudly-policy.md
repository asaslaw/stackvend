# Fail-Loudly Policy

This page is the one written rule for how StackVend platform code handles a step that did not work: when it must **stop with a typed error**, and when it may **carry on with a recorded warning**. It applies to every service, MCP server, job, workflow and install script. Every rule below is already followed in the code; the examples show where. Where this page and the code disagree, the code wins (please fix the page).

**The test.** If the step did not do what it claims, would a later stage, an operator or a user act on something false (a project that is not billed, a check that did not run, a commit that does not exist, a URL nobody served)? If yes, **stop with a typed error**. Carry on only when the step is not security- or correctness-relevant, something later redoes or verifies it, and the problem is recorded where an operator will see it.

---

## 1. Stop with a typed error (the default)

**1.1 Every failure has a type, not just a message.** A failure carries a class, a stage and an HTTP status, so the workflow, the dead-letter record and the Control Center can show what happened without parsing text.

* `apps/orchestrator-gateway/gate_errors.py`: `ErrorClass` and the `GateError` family. `GateFailedError` (`CODE_DEFECT`, 422) is the only class that may loop back to the developer; `GateUnavailableError` (`GATE_UNAVAILABLE`, 503) and `PlatformDefectError` (`PLATFORM_DEFECT`) stop the run.
* Agent stages (`apps/orchestrator-gateway/stage_deadline.py`, `stage_jobs.py`, `stage_runner.py`): `STAGE_DEADLINE_EXCEEDED` (504: the stage ran out of its budget; the body carries its progress), `STAGE_ABANDONED` (409: the run ended, a newer job took the stage or the emergency stop is on), `STAGE_INTERRUPTED` (503: the stage-runner job was stopped, or ended without an answer), `STAGE_TIMEOUT` (the workflow waited the full budget, no answer). All four stop the run, never loop back to the developer, and nothing is committed after them; the Control Center's debrief says to relaunch.
* `apps/project-vending/vending.py`: `VendingFailure(error_class, detail)`, for example `BILLING_NOT_LINKED`. The `REDEPLOY_*` classes in the same file are chosen by HTTP status and exception type only, never by message text (invariant 2: no string-matching heuristics).

**1.2 "Could not check" is never "passed".** A gate, validator or judge that cannot run reports itself unavailable. It never returns a pass, and the run does not regenerate code to get past it.

* `apps/orchestrator-gateway/developer_agent/validators/base.py`: a validator that raises `ValidatorUnavailable` makes the report UNAVAILABLE (`GATE_UNAVAILABLE`).
* `apps/orchestrator-gateway/main.py`: `_fetch_pipeline_context_for_qa` raises `GateUnavailableError` when the stored Task DAG is missing. It does not judge the code against an empty, made-up DAG. `HclUnavailable` in `apps/orchestrator-gateway/developer_agent/access_policy_validator.py` treats a missing HCL parser as a deployment defect, never as a skip.

**1.3 Success is one exact word.** A worker succeeds only when it explicitly reports `SUCCESS`. Missing, partial or unknown outcomes count as failures.

* `shared/callbacks.py`: `guaranteed_callback_scope` delivers `SUCCESS` only for a status in `SUCCESS_STATUSES` (exactly `{"SUCCESS"}`). A worker that never sets a status ends FAILED with `WORKER_NO_OUTCOME`, and an unrecognized status ends FAILED with the original word kept in `reported_status`. An outcome whose callback could not be delivered (any status) is kept with its callback URL in `pipeline_executions/<trace>/undelivered_callbacks`, with every OpenTofu output the engine marks sensitive masked; while the run's workflow is still waiting, the gateway's build admission and the Control Center's active-runs poll send it again (`redeliver_undelivered_callbacks`). In practice that is a `SUCCESS`: an undelivered `FAILED` outcome has already ended the run, so neither poll picks it up. A redelivery that cannot succeed ends typed (`CALLBACK_URL_REJECTED`, or `CALLBACK_REDELIVERY_EXHAUSTED` after 5 attempts) and is written on the run record as `callback_redelivery_error`.
* `mcp-servers/terraform/service.py`: an apply that fails, for example on a Cloud Run startup probe, is reported FAILED with the engine's text. It is not turned into a success because some revision of the service is Ready: the apply stopped part-way.

**1.4 No fabricated ids, URLs or records.** Never put a placeholder commit SHA, pull-request URL, folder record, region or default value where a real one belongs. If the real value is not available, raise.

* `apps/orchestrator-gateway/developer_agent/handler.py`: with no VCS credential, the developer stage raises `GateUnavailableError` with reason `VCS_CREDENTIAL_UNAVAILABLE`. It does not report a pretend commit with a made-up pull-request URL.
* `apps/orchestrator-gateway/main.py`: `resolve_service_url` returns a platform service's URL from its env override or the Cloud Run Admin API, else raises `ServiceUrlUnavailable` (reason `SERVICE_URL_UNKNOWN`). It never builds a URL from a hash, a port or a default region. The Control Center's `get_git_server_url` likewise returns the real Serverless Git server URL or nothing, and the workload details then carry `GIT_SERVER_URL_UNKNOWN` instead of a clone URL.
* `shared/providers/serverless_git_provider.py`: `fetch_file_content` raises `ServerlessGitNotFound` when the repository or branch is missing, and never reads another branch in its place. `RegionUnavailable` in `apps/orchestrator-gateway/developer_agent/terraform_engine.py` is raised when no platform region is configured, so no region is guessed (invariant 3).
* `shared/settings.py`: `workload_region` returns a workload's recorded region only when it is in the approved deployable regions, else raises `RegionNotApproved` (`REGION_NOT_APPROVED`, with the stage, the region and the approved list); it never substitutes another region. The Control Center's create route refuses a region outside the list (`REGION_NOT_APPROVED`, 422), a region the chosen regulated baseline does not allow (`REGION_PROFILE_CONFLICT`, 422) and a different region for an existing workload (`REGION_CHANGE_REFUSED`, 409) before anything is written or vended; an Express run whose region cannot be established stops before vending (`REGION_NOT_APPROVED` / `REGION_UNAVAILABLE`). A Settings save is refused when it adds a region Cloud Run does not offer (`REGION_UNKNOWN`, 422), removes a region a workload still uses (`REGION_IN_USE`, 422) or cannot check either (`REGION_LOOKUP_UNAVAILABLE`, 503): nothing is stored.
* `mcp-servers/terraform/service.py`: a deploy reads the workload's recorded region through `resolve_workload_region` (the settings helper above, against the approved list read with the server's own Firestore client). A recorded region that is not approved stops the deploy before anything is fetched, built or applied (`REGION_NOT_APPROVED`, `operator_required`, with the approved list); settings or a workload record that cannot be read for that check stop it with `REGION_UNAVAILABLE` (`operator_required`). It never deploys into the install's default region instead. A workload without a recorded region keeps the platform region exactly as before.
* The workload's own region downstream of creation (FD-7M-a): the developer stage stops before any model call with `REGION_NOT_APPROVED` when the recorded region is not approved, and with `REGION_UNAVAILABLE` when the workload record or the settings cannot be read to check it, including a service that has no settings store although a project is configured (`resolve_workload_region` in `apps/orchestrator-gateway/developer_agent/terraform_engine.py`). The pre-developer quota check (`/discovery/validate-headroom`) answers 503 `REGION_UNAVAILABLE` when it cannot find exactly one workload for the run, and 422 `REGION_NOT_APPROVED`; both pause the run for an operator, as any unverified quota check does. `/discovery/quotas` answers 503 `REGION_UNAVAILABLE` when the approved list cannot be read and no region was requested; with requested regions it harvests those and logs the class (the snapshot is advisory input to the architect). The FinOps enforcer refuses to scale a workload whose region it cannot establish (`REFUSED`, HTTP 409, with `error_class` `REGION_NOT_APPROVED` or `REGION_UNAVAILABLE`); it never lists or scales Cloud Run services in another region. A refused scale-to-zero writes the usual budget-breach approval card and a billing alert, so the breach that was not enforced is visible to an operator; nothing is recorded as enforced, so the next scheduled run tries again. An in-flight quota claim without a region is not counted in any region (`QUOTA_CLAIM_REGION_MISSING`, logged).
* `mcp-servers/terraform/service.py`: a deploy's service URL is the apply's own output only when the Cloud Run v2 API confirms it (it is a printable string equal, apart from one trailing `/`, to the `uri` or one of the `urls` of a service in the child project's complete listing; `confirm_cloud_run_service_url`), else the API `uri` of the child project's service when the outputs name no URL (`_list_cloud_run_services`, `pick_cloud_run_service_url`). An output that names a URL the API does not confirm is never replaced by a guessed listing URL. When no confirmed URL exists, the deploy still succeeds but reports the URL as unknown: `service_url` is empty, `service_url_unknown_reason` is typed (`CLOUD_RUN_URL_NOT_CONFIRMED`, `CLOUD_RUN_API_UNAVAILABLE`, `CLOUD_RUN_SERVICE_NOT_FOUND` or `CLOUD_RUN_SERVICE_AMBIGUOUS`) and the result's warnings carry `SERVICE_URL_UNKNOWN`. GKE, load-balancer and custom-domain URLs are recorded as unknown the same way. No run.app address is built from ids; the Control Center shows "URL unknown". A workload whose typed topology has no Cloud Run service (only GKE or event-worker kinds) expects no URL, so nothing is looked up and nothing is reported unknown.

**1.5 Security-relevant and destructive steps fail closed.** When a step guards access, billing, ownership or deletion, any doubt means refuse.

* `apps/control-center/sandbox_guard.py`: before the automatic sandbox sweep deletes anything, `assert_sandbox_deletable` must pass. The first failed check raises `SandboxDeletionRefused` and nothing is changed. A Resource Manager error (`CRMUnavailable`) is a refusal, not a retry or a pass.
* `apps/project-vending/vending.py`: if a billing account is configured but cannot be linked, the vend fails with `BILLING_NOT_LINKED` instead of reporting the project vended, because an unbilled project can run nothing. A failed child-owner grant (`_grant_child_project_owners`) also fails the vend.
* `scripts/apply.sh` and `scripts/bootstrap.sh` (`sv_post_plan_check` in `scripts/common/runner_switch_gate.sh`, FD-7L): a plan that moves the Terraform runners to their own service accounts is applied only when every live workload has a READY, vending-signed runner identity that pins its repository (`scripts/common/runner_identity_readiness.py`). Otherwise nothing is applied: `APPLY_RUNNER_SWITCH_NOT_READY` lists the workloads; `APPLY_RUNNER_SWITCH_UNCHECKED` when the guard database, the plan or the signing certificates cannot be read.
* `apps/project-vending/vending.py` `_get_project`: vending's single Resource Manager project reads (the existence check of a recorded project, the ownership check after a 409 on create, the project number) treat only HTTP 403 or 404 as "no such project". A short network error (the same classes and HTTP statuses as the operation polls) is read again for up to 60 seconds; if it lasts, the vend fails with `VENDING.PROJECT_READ_UNAVAILABLE`, naming the project and the read. It is never taken as "not created" (which would create the project again) or "taken by someone else" (which would create a second project under another id). For the existence check and the ownership check after a 409, any other error stops the vend unchanged. The number read of a project not created in this vend keeps the earlier behaviour on any other error (the vend goes on with an empty number), and the number read for the build grants stays warn-and-continue, as before. A project created in the vend whose number is still unknown fails it with `VENDING.PROJECT_NUMBER_UNRESOLVED` (or `VENDING.PROJECT_READ_UNAVAILABLE` when the read stayed transient) instead of going on without provenance; the workload record names the project with the failure, and the message says to delete the project by hand first and then re-run the vend. The number normally comes from the create operation's own answer.
* `scripts/apply.sh` and `scripts/bootstrap.sh` (`sv_post_plan_check` in `scripts/common/runner_switch_gate.sh`, FD-7L): a plan that moves the Terraform runners to their own service accounts is applied only when every live workload has a READY, vending-signed runner identity (`scripts/common/runner_identity_readiness.py`). Otherwise nothing is applied: `APPLY_RUNNER_SWITCH_NOT_READY` lists the workloads; `APPLY_RUNNER_SWITCH_UNCHECKED` when the guard database, the plan or the signing certificates cannot be read.
* `apps/project-vending/vending.py` `_get_project`: vending's single Resource Manager project reads (the existence check of a recorded project, the ownership check after a 409 on create, the project number) treat only HTTP 403 or 404 as "no such project". A short network error (the same classes and HTTP statuses as the operation polls) is read again for up to 60 seconds; if it lasts, the vend fails with `VENDING.PROJECT_READ_UNAVAILABLE`, naming the project and the read. It is never taken as "not created" (which would create the project again) or "taken by someone else" (which would create a second project under another id). For the existence check and the ownership check after a 409, any other error stops the vend with `VENDING.PROJECT_READ_FAILED` (the error's class and HTTP status, chained to it). The number read of a project not created in this vend keeps the earlier behaviour on any other error (the vend goes on with an empty number), and the number read for the build grants stays warn-and-continue, as before. A project created in the vend whose number is still unknown fails it with `VENDING.PROJECT_NUMBER_UNRESOLVED` (or `VENDING.PROJECT_READ_UNAVAILABLE` when the read stayed transient) instead of going on without provenance; the workload record names the project with the failure, and the message says to delete the project by hand first and then re-run the vend. The number normally comes from the create operation's own answer.
* `apps/project-vending/vending.py` `vend_gcp_project` never makes a second project for, or silently adopts, a project StackVend may already own. It decides only by where the project id came from and by typed Resource Manager fields (`state`, `labels`, the project number) and the provenance record:
  * a workload record that cannot be read when the vend starts stops it before anything is created (`VENDING.WORKLOAD_RECORD_UNREADABLE`): the record says which project the workload already owns, so it is never taken for "no record";
  * a project that a `PROVISIONED` or `ACTIVE` workload record names, but that answers 403 or 404, is not created again (project ids are never reusable, so that could only end in a second project under a fallback id): `VENDING.RECORDED_PROJECT_UNREADABLE`. A new or pre-assigned id still gets the fallback id after a 409 and a 403 or 404, as before;
  * a recorded project, or one found after a 409, that is pending deletion (`DELETE_REQUESTED`) stops the vend with `VENDING.PROJECT_PENDING_DELETION`;
  * the target project id is written on the workload record before each `projects.create`, with a `vend_target` marker (the id, the trace and the time), so a vend that stops after Google created the project is re-run against the same id; if that write fails, the vend stops before anything is created (`VENDING.PROJECT_TARGET_UNRECORDED`). A later vend whose create of the marked id answers 409 and whose read answers 403 or 404 stops with `VENDING.VEND_TARGET_UNREADABLE` instead of creating a fallback project (the earlier create may not be visible yet; a `DECOMMISSIONED` record's marker is ignored);
  * after a 409, an existing project that carries this workload's StackVend labels is adopted only when its provenance record names exactly that project; otherwise the vend stops with `VENDING.PROJECT_UNPROVENANCED` (delete the project by hand, or have the owner record its provenance, then re-run), or with `VENDING.PROJECT_PROVENANCE_UNREADABLE` when the record cannot be read;
  * after a 409, an existing project whose `stackvend-product-id` label names another workload is never adopted: `VENDING.PROJECT_LABELLED_FOR_OTHER_PRODUCT` (an operator resolves the id clash). A project without a `stackvend-product-id` label is adopted as before.
* `mcp-servers/terraform/service.py`: before a deploy builds anything, every variables file OpenTofu would load by itself from the deploy root besides the platform's own (`terraform.tfvars.json`, `*.auto.tfvars`, `*.auto.tfvars.json`; `workspace_auto_tfvars_findings`) must be a regular file whose variable names the platform can list and must not set a platform-owned variable (`PLATFORM_OWNED_TFVARS`), because it would override the platform's values. Otherwise the deploy stops for an operator (`operator_required`: a developer regeneration does not change a file a person committed) with `APPLY.TFVARS_SYMLINK`, `APPLY.TFVARS_OVERRIDES_PLATFORM` or `APPLY.TFVARS_UNPARSEABLE`, naming the file and the variable. A file the platform cannot read is never passed as unchecked, even when OpenTofu's parser accepts it.
* `mcp-servers/terraform/service.py`: on every saved plan of a deploy, each variable the platform supplies that the root module declares must have exactly the platform's input value in the plan's own `variables` (`root_variable_overrides`, DEPLOY-ROOT-VARS). A different value, or none, stops the deploy for an operator with `APPLY.ROOT_VARIABLE_OVERRIDDEN` (class `TFVARS_OVERRIDES_PLATFORM`) naming the variable, never its value, before anything is imported or applied.
* `mcp-servers/terraform/service.py` (GHA-DEPLOY-SWITCH): a workload whose GitHub Actions deploy switch is off is never deployed with its identity federation kept. If its committed infrastructure code was generated while the switch was on (the root module does not declare `enable_github_actions_deploy`), the deploy stops with `APPLY.GHA_DEPLOY_SWITCH_NOT_IN_IAC` (`operator_required`: no automatic developer run; the workload's next pipeline run regenerates the root) before anything is built; a stored switch that is not true or false stops it with `GHA_DEPLOY_SWITCH_INVALID` (`operator_required`). The developer stage refuses the same invalid value (`PlatformDefectError`, reason `GHA_DEPLOY_SWITCH_INVALID`).
* `mcp-servers/terraform/service.py` (FD-55 W6e): the deploy no longer edits committed Terraform, so two cases that used to be rewritten stop typed (class `IAC_DEFECT`, the developer's bounded repair) and name what to fix. A Cloud Run service that the saved plan creates or updates with the environment variable `PORT` (Cloud Run sets it and rejects it) stops before any import or apply with `APPLY.RESERVED_ENV_PORT` (`reserved_env_port_findings`). Terraform files under the old `infra/workloads/` folder beside another root configuration (`infra/workload/`, the repository root or the deploy request) stop the deploy before anything is built with `APPLY.PLURAL_WORKLOADS_NOT_APPLIED`, listing the files.
* `apps/project-vending/runner_identity_backfill.py` (FD-7L, Per-workload installs only). The backfill and state migration report a typed class for each workload:
  * `BACKFILL.NO_PROVENANCE`, `BACKFILL.IDENTITY_UNVERIFIED`, `BACKFILL.NO_RIGHTS_ON_PROJECT` (vending lacks a project-level right on the workload's project: `iam.serviceAccounts.create`, `iam.serviceAccounts.setIamPolicy`, `resourcemanager.projects.setIamPolicy` or `storage.buckets.create`; nothing is written)
  * `BACKFILL.NO_RIGHTS_ON_BUCKET` (vending lacks a right on the workload's state bucket, checked on the bucket once it is found or created: `storage.buckets.getIamPolicy` / `setIamPolicy`, `storage.objects.list` / `get` / `create` / `delete`; a project owner holds them through the bucket's default project-owner bindings. The bucket's IAM and objects are not touched and no record is written). A dry run that would stop at either check reports `DRY_RUN_STOP` with that class and lists nothing after it.
  * `BACKFILL.APIS_MISSING`, `BACKFILL.SA_CREATE_FAILED`, `BACKFILL.GRANT_FAILED`, `BACKFILL.BUCKET_NAME_TAKEN`, `BACKFILL.BUCKET_FAILED`
  * `BACKFILL.NOT_PROVISIONED`, `BACKFILL.NOT_MIGRATED`, `BACKFILL.PURGE_TOO_EARLY`, `BACKFILL.STEPS_INVALID`, `BACKFILL.REAL_RUN_TOO_LARGE` (a real run names at most 3 workloads), `BACKFILL.AUDIT_UNAVAILABLE`
  * the repository pin (step `ensure_repository`, once the record is READY): `BACKFILL.REPOSITORY_UNKNOWN` (the workload record names no owner/name repository or no known `vcs_provider`), `BACKFILL.REPOSITORY_ID_UNKNOWN` (a GitHub repository without its recorded id), `BACKFILL.REPOSITORY_NAME_DIFFERS` (the recorded `github_repo` is not the name vending pins: for Serverless Git `castor/<product id>`, for GitHub the name the deploy resolves), `BACKFILL.REPOSITORY_MISMATCH` (the record already pins another repository; it is never overwritten), `BACKFILL.WORKLOAD_UNREADABLE`. Nothing is pinned; a full-build re-vend pins it. The step-B readiness check (`scripts/common/runner_identity_readiness.py`) and the Settings card report a READY record without a pinned repository as `REPOSITORY_NOT_PINNED`.
  * `STATE_LOCKED`, `STATE_MIGRATION_BUSY`, `STATE_MIGRATION_CONFLICT`, `STATE_MIGRATION_RACE`, `STATE_MIGRATION_UNREADABLE`, `STATE_MIGRATION_LOCK_FAILED`, `STATE_COPY_FAILED`, `STATE_RESTORE_INCOMPLETE`, `STATE_PURGE_INCOMPLETE`
  * `RUNNER_RECORD_UNSIGNED`, `RUNNER_TARGET_MISMATCH`

  Before anything is copied, a failure puts the record back as it was. After a copy, the workload stays `MIGRATING`, with the cursor and the class recorded, and the next run resumes from the cursor. A configuration error stops the whole run with HTTP 503 (for example a broker identity shared with the runners, an unavailable guard database, or signing or certificates that are unavailable).
* `apps/project-vending/vending.py` `decommission_workload` (FD-7L, Per-workload installs only):
  * When the state archive copy fails, the decommission stops before the delete (`DECOMMISSION_STATE_ARCHIVE_FAILED`). The only exception is an approval minted with "delete without archive".
  * A request for "delete without archive" whose approval does not carry that option is refused (`DELETE_WITHOUT_ARCHIVE_NOT_APPROVED`).
* The FD-7L state readers never fall back to another bucket when a runner identity record cannot be trusted:
  * the Control Center (`services/runner_state.py`) shows no state;
  * rollback answers `ROLLBACK_UNAVAILABLE` and names the class.
* `shared/express_synthesizer.py` raises `ExpressRunnerIdentityModeInvalid` for an unknown `STACKVEND_TF_RUNNER_IDENTITY` value (`RUNNER_IDENTITY_MODE_INVALID`).
* `mcp-servers/terraform/service.py` (FD-7L Phase 2b). Every run (deploy, plan, saved-plan apply, drift check, force-unlock) stops for an operator (`operator_required`) before OpenTofu starts:
  * with `RUNNER_IDENTITY_MODE_INVALID` when `STACKVEND_TF_RUNNER_IDENTITY` holds an unknown value;
  * on a Per-workload install, when the workload's state location cannot be trusted: `RUNNER_IDENTITY_NOT_READY` (no runner identity record, or not `READY`), `STATE_MIGRATION_IN_PROGRESS` (`MIGRATING`), `RUNNER_STORE_UNAVAILABLE` (the guard database cannot be read), `RUNNER_RECORD_UNSIGNED` / `RUNNER_RECORD_KEY_RETIRED` / `RUNNER_RECORD_UNVERIFIABLE` (the vending signature does not verify), `RUNNER_TARGET_MISMATCH` (the run targets another project than the signed record), `STATE_BACKEND_MISMATCH` (a drift workspace prepared for another bucket). It never falls back to the platform bucket.
  * Pre-init policy (Per-workload installs): workload Terraform that sets a provider setting outside the exact allow-list, has its own backend, `cloud` or state `encryption` block, a `backend.tofu` file, a non-local module or a remote-state read of another state, or a file the platform's parser cannot read, stops before `init` with `APPLY_CONTENT_POLICY` and the codes `POLICY.PROVIDER_ATTRIBUTE_FORBIDDEN`, `POLICY.BACKEND_NOT_PLATFORM`, `POLICY.STATE_ENCRYPTION_FORBIDDEN`, `POLICY.MODULE_SOURCE_NOT_LOCAL`, `POLICY.REMOTE_STATE_FORBIDDEN`, `APPLY.SOURCE_UNPARSEABLE` (neither the platform's parser nor OpenTofu's own reads the file) and `APPLY.SOURCE_NOT_CHECKABLE` (valid OpenTofu that the platform's reader cannot check; refused all the same, with the line; each finding names its file).
  * Content policy (Per-workload installs): a plan that would manage the deployer account (any service-account name form, including one the platform cannot resolve), its keys or grants, grant `roles/owner`, `roles/editor` or `roles/iam.serviceAccountTokenCreator` at project level, remove the owner role, attach a deny policy or touch or import a state bucket is refused with `APPLY_CONTENT_POLICY` / `POLICY.PLATFORM_IDENTITY_TOUCHED`. A value unknown at plan time passes only as a plain reference to a service account or bucket created in the same module whose name is known and safe; anything else is refused. The self-healing import never adopts the deployer account, a state bucket or the `<project>-cloudbuild-source` bucket (an unresolved adoption, `APPLY_ADOPTION_UNRESOLVED`).
  * On a Shared install after step A (a switch back from Per workload), a workload whose READY runner identity record names its own state bucket, where `default.tfstate` is live while the platform bucket holds none for it, is refused with `STATE_IN_CHILD_BUCKET` (a Shared run would start from an empty state; copy the state to the platform bucket first, or switch back to Per workload). When those objects cannot be read: `STATE_LOCATION_UNREADABLE`; the guard database: `RUNNER_STORE_UNAVAILABLE`. A workload whose project is being deleted may answer `STATE_LOCATION_UNREADABLE`; decommission it instead of deploying.
  * `force_unlock` (every install) reads the lock object first (a transient read error is read again) and refuses StackVend's state-migration tombstone and migration lock (`STATE_MOVED_DO_NOT_UNLOCK`); a lock it still cannot read is refused too (`STATE_LOCK_UNREADABLE`). The `STATE_LOCKED` message for those two locks names no force-unlock. On a Per-workload install the deploy's pre-flight lock read uses the workload's brokered deployer and a failed read stops the deploy (`STATE_LOCK_UNREADABLE`); a Shared install proceeds as before. A saved-plan apply whose workspace was prepared for another bucket is refused (`STATE_BACKEND_MISMATCH`).
* The Terraform runner identity mode (FD-7L-F4, `shared/runner_identity.py` `runner_identity_mode`) is never guessed. On an install that declares Shared, every reader (vending, the Control Center, the Terraform server and job, rollback) uses vending's signed record `install_settings/runner_identity` in the guard database; no record means Shared only while the change log `install_settings/runner_identity/changes` is empty (the mode was never switched). Otherwise the reader stops with a typed class instead of a default: `RUNNER_MODE_RECORD_MISSING` (the record is gone after a switch), `RUNNER_MODE_RECORD_STALE` (the record is not the one the newest change entry wrote, for example an older signed record put back), `RUNNER_STORE_UNAVAILABLE` (guard database not readable, or not configured on a service that step A configured), `RUNNER_RECORD_UNSIGNED`, `RUNNER_RECORD_UNVERIFIABLE`, `RUNNER_RECORD_KEY_RETIRED`, `RUNNER_MODE_RECORD_INVALID` (signed, but not a valid mode record). The Settings card also reports a change entry that does not verify (`RUNNER_MODE_TAMPERED`) as a warning, and a change entry whose version no switch can outrank, or that is not a number, as `RUNNER_MODE_LOG_CORRUPT` with the document a project owner removes in the console (a switch is refused with the same class while such an entry blocks it). A vend stops with `VENDING.RUNNER_IDENTITY_MODE_UNREADABLE` (the reader's class in the detail); an Express run stops at synthesis with the reader's class; rollback answers `ROLLBACK_UNAVAILABLE`.
* Changing that mode (Control Center Settings, through vending) is refused with nothing written: `RUNNER_IDENTITY_MODE_RETIRED` (the install declares Per workload; the mode is final), `RUNNER_IDENTITY_STEP_A_MISSING` (Per workload before the platform's step A), `RUNNER_MODE_CHANGED` (someone else changed it; reload), `RUNNER_MODE_SWITCH_BUSY` (a Terraform run may be in flight: an IN_FLIGHT terraform stage in `pipeline_executions` or a running tf-applier execution, of any workload; a read error counts as busy), `RUNNER_MODE_CHANGE_INVALID` (bad request), and in the Control Center `HUMAN_ADMIN_REQUIRED`, `RECENT_SIGN_IN_REQUIRED`, `RECENT_SIGN_IN_UNAVAILABLE` (behind Identity-Aware Proxy, which does not pass the sign-in time) and `RUNNER_MODE_CONFIRMATION_MISMATCH`.
* The terraform runner (`mcp-servers/terraform/service.py`, `applier.py`, `runner_credentials.py`; FD-7L, Per-workload installs only) never runs workload OpenTofu, or a call into a workload project, with the platform's own identity. Every refusal is `operator_required`:
  * `RUNNER_IDENTITY_NOT_REGISTERED`: no brokered deployer credentials for the workspace (a deploy, a tofu command or a child call outside a tf-applier execution that vending dispatched).
  * `RUNNER_IDENTITY_NOT_READY`: the job is not configured for brokered runs (no `RUNNER_NONCE`, `VENDING_SERVICE_URL`, guard database or execution name), or the workload has no READY runner identity record.
  * `RUNNER_RECORD_UNSIGNED` (also `RUNNER_RECORD_KEY_RETIRED` / `RUNNER_RECORD_UNVERIFIABLE`), `RUNNER_TARGET_MISMATCH` (the dispatch record, the workload record or the deploy's target disagrees with vending's signed provenance), `STATE_BUCKET_NOT_OWNED` (the recorded state bucket is not a bucket of the workload project).
  * `RUNNER_MODE_UNSUPPORTED`: a dispatch the job does not run: saved-plan apply and drift (not executions yet), a saved plan, a workflow deploy that carries a staged payload, or a synchronous run without one.
  * `RUNNER_BROKER_UNAVAILABLE`: the broker could not renew the deployer token before it ran out; the running OpenTofu command is interrupted (SIGINT, so the state lock is released) and nothing more runs. A shorter broker outage is ridden out on the current token.
  * A refusal before the dispatch record is read (no callback URL is known yet) fails the execution with the typed class in its log; afterwards the workflow callback carries it.
  * `RUNNER_EXECUTION_NOT_DISPATCHED`: an execution started with the Shared inputs (`CALLBACK_URL`, no `RUNNER_NONCE`) on an install that is now Per workload (a deploy started just before a mode switch). Nothing is deployed; the FAILED callback goes to that `CALLBACK_URL` through the guaranteed callback (a token only ever goes to this platform's Workflows callback endpoint). The other way round, an execution vending dispatched (`RUNNER_NONCE`, no `PRODUCT_ID`) that starts on a Shared install logs `RUNNER_NONCE_ON_SHARED_INSTALL` and ends; the terraform server's dispatch watcher reports it. A job that cannot read the runner identity mode never falls back to the Shared path when it has a `RUNNER_NONCE` (the reader's class is logged; the watcher reports it) or a `CALLBACK_URL` (the FAILED callback carries the reader's class).
  * The old job inputs (`PRODUCT_ID`, `TARGET_PROJECT_ID`, `CALLBACK_URL`, ...) are ignored on a Per-workload install and named in one `RUNNER_ENV_IGNORED` log line.
  * Repository read (FD-7L Phase 4): the deploy reads only the repository that vending's signed record pins, before anything is built. It reads GitHub with vending's read-only token and Serverless Git with the job's own ID token. It stops with `RUNNER_REPOSITORY_NOT_PINNED` when the record pins no readable repository, and with `RUNNER_TARGET_MISMATCH` when the deploy names another repository, names a branch that is not a well-formed git branch name (checked before any token or call), or vending's token is not exactly `contents: read` for it. A refusal of vending's `/runner/repo-token` keeps vending's class (for example `RUNNER_REPO_TOKEN_UNSUPPORTED`; an unavailable broker is `RUNNER_BROKER_UNAVAILABLE`). A tree it cannot read completely is `REPO_TREE_INCOMPLETE`; this includes a repository of more than 2,500 files (refused before any file is read) and a GitHub rate limit that outlasts the read's bounded wait. The only retry on this path is that wait: a 403 or 429 answer whose GitHub headers ask for a wait (`Retry-After` in seconds, or `X-RateLimit-Remaining: 0` with `X-RateLimit-Reset`; never the answer's text) is repeated after that wait, at most 3 times per call, never for a wait over 60 seconds and never past 180 seconds of waiting for the whole read; the error then names the headers and why it stopped. Any other answer is not retried, and there is no fallback (redeploy). It never falls back to `GITHUB_TOKEN`, the GitHub App key or another reader. `GITHUB_TOKEN`, `CASTOR_GIT_AUTH_TOKEN` and `GOOGLE_OIDC_ID_TOKEN` in the environment are ignored and named (never their values) in a `RUNNER_ENV_IGNORED` line.
* The terraform server's `/deploy-async` (`mcp-servers/terraform/main.py`, `runner_dispatch.py`; FD-7L Phase 5a) never runs a deploy in its own container when the tf-applier job cannot be started. On every install a failed dispatch is `TF_APPLIER_DISPATCH_FAILED` (`operator_required`), with a `cause` (the Cloud Run or vending refusal) and `outcome_unknown` set when the request may have started an execution whose answer was lost (check the job's executions for the trace before a relaunch). On a Shared install the Cloud Run RunJob failure is classified by exception type, HTTP status and the API's own JSON status body: a refusal the API made itself started nothing; only a quota or availability refusal is retried, at most 3 times in all (after 2, 4 and 8 seconds, never again through the other transport): on the SDK (gRPC, the default transport) a `ResourceExhausted` (429) error, which the API raises before it creates anything; on REST a 429 or 503 whose body is the API's own status (`RESOURCE_EXHAUSTED` / `UNAVAILABLE`). A gRPC `UNAVAILABLE` carries no such body and is treated as ambiguous, so on the default transport a transient 503 stops for the operator; a timeout, a gateway answer without that body or any other ambiguous failure is never retried and is never followed by a second RunJob. A job switched off by configuration (`ENABLE_TF_APPLIER_JOB=false`, local runs and tests) still deploys in-process. On a Shared install the failure arrives in the workflow callback. On a Per-workload install the deploy is dispatched through vending before the answer, and every refusal is the HTTP answer (the workflow stops on it):
  * `TF_APPLIER_DISPATCH_FAILED` with vending's code as `cause` (for example `RUNNER_IDENTITY_NOT_READY`, `RUNNER_DISPATCH_FAILED`); the call is never retried, so one deploy never starts two executions. Because this dispatch answers synchronously, a server instance that stops, or a workflow HTTP call that gives up, after vending started the execution leaves the workflow stopped while that execution runs (its later callback finds no waiting workflow); the server logs the execution name with the trace, so the operator can match them.
  * `RUNNER_MODE_UNSUPPORTED`: caller-supplied `hcl_files` on `/deploy-async` (they reach an execution only as the staged payload of a synchronous `/deploy`, FD-7L Phase 5b).
  * `RUNNER_TARGET_MISMATCH` (a request `target_project_id` that is not the project of vending's signed record), `RUNNER_RECORD_UNSIGNED` (and `_KEY_RETIRED` / `_UNVERIFIABLE`), `RUNNER_IDENTITY_NOT_READY` (no READY record, an unreadable record, or `VENDING_SERVICE_URL` / the guard database not configured on the server).
  * `TF_APPLIER_EXECUTION_FAILED_BEFORE_REDEEM` (`operator_required`): the dispatched execution ended, never started, or was refused before it redeemed its nonce, so it knows no callback URL. The server that dispatched it (or any other instance, in a periodic sweep) reads vending's signed dispatch record once the redeem window has passed and, when it is still not redeemed, sends this FAILED callback once to the record's callback URL with its own identity. A redeemed run is never reported (its execution sends its own callback). A watch is claimed in a Firestore transaction before anything is sent, so it is reported at most once. A missing, forged or never verifiable record is not trusted: no callback is sent and the error is logged for the operator. After 24 hours a watch is dropped (the workflow has timed out by then).
  * Synchronous runs (FD-7L Phase 5b, `runner_runs.py`): on a Per-workload install the sync `/deploy` (Express, vending redeploy), both force-unlock routes, `/plan` and the MCP plan tool run in one tf-applier execution each, dispatched through vending without a callback URL; nothing credentialed runs in the server. The request's inputs (Express files, destroy approval, engine, lock ID, the request's deadline) are one staged payload object in the host staging bucket, created once by the server; vending signs its sha256 into the dispatch record. The server answers from the execution's result document `runner_results/<dispatch_id>`, with the same answer shapes as an in-process run. Refusals: `RUNNER_PAYLOAD_UNCONFIGURED` (no staging bucket on the server or job, plan step A; nothing dispatched), `RUNNER_IDENTITY_NOT_READY` (no broker identity to verify vending's records; nothing dispatched), `RUNNER_PAYLOAD_STAGING_FAILED` (the server could not create the payload object; nothing dispatched), `RUNNER_PAYLOAD_MISMATCH` (the execution's payload bytes, sha256, bucket, mode, product, trace or file keys differ from the signed record; checked before any credential is minted), `RUNNER_PAYLOAD_UNREADABLE` (the execution could not read the payload), `RUNNER_SYNC_DEADLINE_PASSED` (the execution started after the request's deploy budget ran out; nothing deployed), `RUNNER_RESULT_TIMEOUT` (504: no result before the request's deadline; the execution may still run, so an operator checks it and the workload's state before a retry), `RUNNER_RESULT_MISMATCH` (502: a result document that is not this run's, one whose dispatch record does not verify or binds another execution, or one whose sha256 is not the result fingerprint vending signed into the dispatch record; the answer says to check the execution and the workload's state. Before it writes its result document the execution has vending sign the sha256 of the result (`/runner/result`, session-bound, once), so a writer of the default database can no longer substitute the answer; a document that appears before vending's signed record shows the redeem and the fingerprint is not used and does not end the wait), `RUNNER_RESULT_NOT_RECORDED` (logged by the execution when vending does not sign its result fingerprint, in which case it writes no document, or when it cannot write the document), `RUNNER_RESULT_INVALID` (422, vending: a fingerprint that is not a sha256) and `RUNNER_RESULT_ALREADY_SIGNED` (409, vending: a different fingerprint is already signed for that run), `TF_APPLIER_EXECUTION_ENDED_WITHOUT_RESULT` (502: vending reports, through `/runner/dispatch-status`, that the redeemed execution ended a minute ago and no accepted result appeared; it may have applied changes, so an operator checks the workload's state before a retry), and `TF_APPLIER_EXECUTION_FAILED_BEFORE_REDEEM` (502) when vending's signed record shows the execution never redeemed its nonce after the redeem window, or vending reports it ended without a redeem (it applied nothing). `RUNNER_DISPATCH_STATUS_UNAVAILABLE` is a log line only: the server could not ask vending for the execution's state and keeps waiting. A plan run answers as the in-process `/plan` does (its result, with `saved_plan_kept: false`: the saved plan is deleted with the execution); the one-way engine gate comes back as `IAC_ENGINE_DOWNGRADE_BLOCKED` in the result and is answered as the in-process HTTP 400. Saved-plan `/apply`, `/drift-check` and the MCP drift tool are refused with `RUNNER_MODE_UNSUPPORTED` (422) on a Per-workload install until they are executions too (they need the workspace of an earlier run); Shared installs run all of these routes in-process as before.
  * `RUNNER_NOT_SINGLE_TENANT` (tf-applier, `service.py`): a second workload's brokered credentials in one process are refused; the local metadata endpoint's isolation unit is the container.
  * Every workload route (`/deploy`, `/deploy-async`, `/plan`, `/apply`, `/drift-check`, both force-unlock routes, `/mcp`) accepts only a Google-signed ID token for this service from an allow-listed caller (`TF_SERVER_WORKLOAD_CALLERS`, else the workflow, gateway, Control Center and vending accounts of the host project): `UNAUTHENTICATED` (401), `CALLER_NOT_ALLOWED` (403), `CALLERS_UNCONFIGURED` (503), each logged as a security event. An unknown runner identity mode refuses these routes (`RUNNER_IDENTITY_MODE_INVALID`, 503). `/validate` and `/health` stay open. The list holds service accounts only, so a person calling these routes directly (for example with `gcloud auth print-identity-token`) is refused with `CALLER_NOT_ALLOWED`; operators act through the Control Center, whose account is listed.
* `scripts/upgrade.sh` (FD-4DA) stops with a class and its stage, then prints exactly one next command:
  * before anything changes: `UPGRADE_USAGE`, `UPGRADE_TAG_INVALID`, `UPGRADE_NO_TARGET` (no explicit `PROJECT_ID` / `TFVARS_FILE`; gcloud config is never used), `UPGRADE_REGION_MISMATCH`, `UPGRADE_DIRTY_TREE`, `UPGRADE_NOT_A_CHECKOUT`, `UPGRADE_REMOTE_MISSING`, `UPGRADE_TFVARS_UNREADABLE`, `UPGRADE_PREREQ_MISSING` (also: to verify the signature, no `ssh-keygen`, git older than 2.34 or OpenSSH older than 8.2), `UPGRADE_GIT_UNREADABLE`, `UPGRADE_NO_TRUSTED_KEYS` (the checkout has no `scripts/release/allowed_signers`; the next command is the explicit `--trust-unsigned` run), and `UPGRADE_GUARD_REFUSED` when one of `scripts/apply.sh`'s own target guards refuses;
  * `UPGRADE_FETCH_FAILED` (a local tag that points elsewhere is never moved), `UPGRADE_TAG_NOT_FOUND`, `UPGRADE_TAG_NAME_MISMATCH` (from `0.9.1-preview.2`: the name inside the tag object is not the requested tag), `UPGRADE_SIGNATURE_INVALID` (the tag is unsigned, lightweight or signed by a key that is not in the installed checkout's `scripts/release/allowed_signers`; nothing of the release has run), `UPGRADE_CHECKOUT_FAILED`, `UPGRADE_PLAN_FAILED`, `UPGRADE_NEEDS_TERMINAL`, `UPGRADE_DECLINED`, `UPGRADE_APPLY_FAILED`, `UPGRADE_DEPLOY_FAILED`;
  * after the deploy, the read-only smoke check: `UPGRADE_SMOKE_UNREADABLE`, or `UPGRADE_SMOKE_FAILED` with the findings `SMOKE_NO_PLATFORM_SERVICES`, `SMOKE_SERVICE_NOT_READY`, `SMOKE_NEWEST_REVISION_NOT_READY`, `SMOKE_STAMP_MISSING`, `SMOKE_STAMP_MISMATCH` (`scripts/common/upgrade_smoke.py`), and `UPGRADE_TFVARS_UNREADABLE` when the release's variables cannot be evaluated (the stamp check never skips silently). It never reports an upgrade done that it could not check.
  * Ctrl-C or a kill: `UPGRADE_INTERRUPTED` with what that stage may have changed (nothing before the apply; a possibly partial apply after it starts); any other unexpected stop after the preflight: `UPGRADE_ABORTED`.

* **Weekly upstream sync** (`.github/workflows/sync-upstream.yml`, runs only when `STACKVEND_UPSTREAM_SYNC` is `true`; the installer no longer offers to turn it on). Before it merges the newest upstream release tag it verifies it (an annotated tag whose own name is that tag, signed by a key in `scripts/release/allowed_signers` of the repository's own default branch); a verification failure stops the run with a typed `SYNC_*` error that names the tag and the manual path. Nothing is pushed, and it never falls back to an older tag.

## 2. Carry on with a recorded warning (the exception)

Degrading is allowed only when **all three** of these hold:

1. the step is not security- or correctness-relevant for anything the platform then reports as done;
2. a later step redoes or verifies it, or an operator has a documented fix;
3. the problem is recorded as **typed data where an operator will look** (the workload record, a Control Center card, the install output), not only in a log line.

Examples:

* **Re-signing the runner identity mode record (FD-7L-F4).** At most once an hour, vending re-signs the mode record (Shared or Per workload) when it is older than 72 hours while it reads the mode. A failed re-sign is logged (`RUNNER_MODE_RESIGN_FAILED`) and the read keeps its own result; the Settings card retries it on every view and shows the outcome (`record_resign`), and `/runner-identity/resign` retries it too. A record whose key has already retired stops every reader (`RUNNER_RECORD_KEY_RETIRED`) until an administrator switches the mode again.
* **Maintenance mode after an upgrade from Settings (SELFUP P3b).** When an upgrade ends where maintenance mode should go back to its earlier value but the settings write fails, the upgrade's own result stands. The failure is recorded on the request (`maintenance.restore_error`), Settings ▸ Upgrades shows `MAINTENANCE_NOT_RESTORED` with **Turn maintenance off**, and every later look at the tab retries the restore. Maintenance stays on meanwhile (no new workload run starts), so nothing is reported as done that is not.
* **API enablement during vending.** `enable_child_apis` in `apps/project-vending/vending.py` never raises. It returns a typed `api_enablement` record (`VENDING.API_ENABLE_FAILED`, `VENDING.API_TABLE_UNAVAILABLE`) that is stored with the vend result, because the workload's first apply enables the same APIs again.
* **Billing grants at install time.** The install never fails over billing-account grants, which need a Billing Account Administrator. `sv_billing_iam_preflight` in `scripts/common/platform_target.sh` makes one read-only permission check and, if it fails, prints `sv_billing_grant_skipped_warning`. `scripts/bootstrap.sh` then prints the exact post-install commands (`sv_billing_post_install_step`), and the Control Center Settings billing card shows which grant is missing. The same fact is a hard stop once something depends on it: vending a child project without a billing link fails with `BILLING_NOT_LINKED` (1.5).
* **Backup of the install's vars file (TFVARS-AUTO-BACKUP).** `scripts/bootstrap.sh` (at the end of an install) and `scripts/apply.sh apply` (after every successful apply) copy `infra/platform/<project_id>.tfvars` to `gs://castor-tfstate-<project_id>/platform/<project_id>.tfvars` (`scripts/common/tfvars_backup.sh`). A copy that cannot be written does not fail the install or the apply: (1) the copy is not part of what was installed or applied, and nothing the platform reports as done depends on it (the local file is unchanged and still drives every run); (2) every later successful apply writes it again, and the warning names the retry, `PROJECT_ID=<project_id> bash scripts/apply.sh apply`; (3) the install output carries the typed warning `BOOTSTRAP_TFVARS_BACKUP_NOT_WRITTEN` or `APPLY_TFVARS_BACKUP_NOT_WRITTEN` with the reason, and the installer repeats it in its Next Steps. The restore side is never degraded: a missing vars file stops `scripts/apply.sh` with a typed error (`APPLY_TFVARS_MISSING`, `APPLY_TFVARS_MISSING_NO_BACKUP`, `APPLY_TFVARS_BACKUP_UNCHECKED`, `APPLY_TFVARS_RESTORE_FAILED`), and a restore stops for review (`APPLY_TFVARS_RESTORED`) instead of applying a file nobody has looked at.
* **A Private (IAP) app with no app administrator (`APP_ADMIN.NONE_CONFIGURED`).** When a Direct IAP Cloud Run workload's admin list is empty (the access record lists none and its verified creator is not a `user:` member), the developer stage still builds it: the platform renders `STACKVEND_APP_ADMIN_EMAILS` as `[]`, and the generated app gives nobody its application-wide administrative role (it never falls back to a first-user bootstrap). The stage logs the warning and records it on the workload as `app_admin_contract` (`admin_count`, `source`, `warning`, a digest of the list, never an address), and the QA judges treat it as configuration, not a code defect. (1) Nothing the platform reports as done depends on an administrator existing; (2) the documented fix is to create the workload from the Control Center as the intended administrator, listed as a `user:` member (see [Known limitations](known-limitations.md#app-administrators-of-a-private-iap-app-cannot-be-changed-yet)), followed by a full build; (3) the warning is typed on the workload record.
* **Validator roll-out.** A validator registered as `report_only` in `validators/base.py` records its diagnostics in the report without blocking, so a new check can be measured before it becomes `blocking`. A `blocking` validator that cannot run is still unavailable, never a pass (1.2).
* **A Task DAG too large to keep for a resume.** The pre-build gate saves the plan for a later `RESUME_DEVELOPER` run, up to a defensive bound of 900,000 bytes for direct callers of the route (the workflow's own 512 KB data limit is lower, so a run through the workflow does not reach it). A larger plan is not saved and the gate still decides, because the copy is needed only by a later resume, never by this build. The three conditions: (1) nothing the platform reports as done depends on the copy; (2) `/agent/resume/outcome` stops a resume of that build with `TASK_DAG_TOO_LARGE`; (3) the record keeps the status `TOO_LARGE`, an explicit Resume shows the reason in a `RESUME_NOT_AVAILABLE` message, and an Auto relaunch that falls back to a full build says so in its toast and in `auto_fallback_reason` on the response and the execution record.
* **FD-7L pre-init and identity policies on a Shared install (owner OQ-32).** On an install still in Shared mode, the terraform server refuses nothing new: each finding of the pre-init policy, of `POLICY.PLATFORM_IDENTITY_TOUCHED` and of the self-healing import's reserved names is logged as one structured `POLICY_WOULD_REFUSE` line, so the operator can count, before switching to Per workload, which live workloads would be stopped (a measurement like the validator roll-out above). The same findings are refusals on a Per-workload install (1.5).

## 3. Healers and sanitizers: Do No Harm

A healer or sanitizer that rewrites generated code may change only what actually fails a real parser or validator (`ast.parse`, an HCL parse, `tofu validate`). Valid input comes back byte-identical, and every healer ships with a negative test that proves it. A healer that cannot repair something leaves it alone, and the validator reports it into the bounded repair loop. The failure is never hidden.

* `append_missing_requirements` in `apps/orchestrator-gateway/gatekeeper_agent/requirements_contract.py` only adds lines: every file that already names what it needs is returned byte-identical.
* `tests/test_anti_hallucination_preflight.py::TestPythonRequirementsPreflightGate::test_substring_triggers_no_longer_inject_requirements` is the matching negative test: words in comments and strings do not trigger a change, and the output equals the input.

## 4. Reviewer checklist

* No `except Exception:` that logs and continues on a step from section 1. If you catch, re-raise a typed error, or show in the PR that all three conditions of section 2 hold and say where the warning is recorded.
* No `or <default>` fallback for ids, regions, URLs, branches, statuses or verdicts.
* A new failure gets a class, a stage and an HTTP status. Classify it by exception type, HTTP status or the step where it happened, never by parsing the message text.
* A new healer gets a negative test (valid input, unchanged output).
